## Findings

### Front-end menu callback bridge — strong

`XC/FE_MNU.TXT` is parsed by `ParseMenu__7MenuMgrR8LineFileP6hdMenu` at
`0x8005FFD0`. Its item directives are constructors, not free-standing labels:
each selector needs matching text objects from the front-end overlay. Overlay 2
later registers button callbacks by the item ID hash in
`SelfInit__9feMenuMgr` at `0x8001103C`. The hash is the ordinary 33x string
hash; useful IDs are `HostDSP = 0xB1AF7E45`, `Display = 0x6FC61216`,
`Sound = 0x061CD029`,
`Sound_Effect = 0x1B5DD3F5`, `Sound_Music = 0xB3DA1CE9`, and
`Sound_Voice = 0xB47983DE`.

The experiment behind `--experimental-host-menu` therefore reuses the stock
`Menu_Sound`, `Sound_Effect`, `Sound_Music`, and `Sound_Voice` objects. A new
logical `HostDSP` menu is inserted into a size-preserving in-memory
`FE_MNU.TXT` overlay, while the unique same-length `Credits\0` string in
`FE.1` becomes the visible `Display\0` label. The CD HLE applies both overlays
only as the matching ISO extents
are copied into guest RAM, leaving the supported BIN/CUE and unpacked files
unchanged.

`PushMenu__9feMenuMgrP6hdMenu` is overlay address `0x80010D08`; its first four
words are fingerprinted as `27BDFFE0 AFB20018 00809021 AFB10014`. The
pre-hook reads the menu hash at `hdMenu+0x0C` and its item-list head at
`hdMenu+0x18`. An `hdSndItemSelection` has its ID hash at `+0x18`, callback at
`+0x10`, current selector index at `+0x30`, display value at `+0x34`, and its
inline display buffer at `+0x38`. The item label object is at `+0x0C` and the
value object at `+0x20`; each active text pointer is selected by the object's
frame byte at `+0x2D` from the table at `+0x38`. Because the Sound and Display
menus share those objects, the hook rebinds the active value pointer and
restores the original Sound labels whenever the real Sound menu is pushed.

The live attempts exposed a second identity hidden by the text format:
`MenuMgr::PushMenu` passes `hdMenu+0x0C` to `PushScreen`. A logical menu named
`Display` collides with the visible front-end identity before the scoped screen
alias and makes the menu disappear when selected. The logical name is therefore
the unique short `HostDSP`, while the user-facing label remains `Display`.
The wrapper call site at `0x80010E0C` aliases only `HostDSP` to `Sound`
immediately before the generic push; the return site at `0x80010E18`
recognizes the host callback on the first selector and restores `HostDSP`.
Delaying the alias until the call site is important: the earlier Sound-specific
branch in `feMenuMgr` must still see the real logical ID or it installs the
retail audio callbacks over the host callbacks.

The next live check showed the shared screen's unreferenced rows behind the
Display selectors. Music now supplies the third Widescreen selector, leaving
only Stereo unused. These are screen-owned text objects, not members of the
Display item list. On a Display push the bridge finds the real Sound menu
through `MenuMgr+0x30` and blanks the Stereo label and active value; a real
Sound push restores them. In the supported `FE.1`, `SOUND OPTIONS` immediately
follows the null-terminated `Stereo` string, so the same fingerprinted object
reference also changes the shared title to `DISPLAY MENU` and restores it to
`SOUND OPTIONS` for audio. Frame Rate and Resolution borrow the Stereo value
object's font and non-translation 3x3 transform components, giving them the
compact ON/OFF style without moving either row. Widescreen retains the Music
row's stock volume-readout style. A Sound push restores the first two rows from
Music as well.

The three Display rows point to reserved HLE address `0x80002FF0`, below
the host patch arena at `0x80003000`. No guest code is stored there: the host
consumes the callback before instruction fetch, reads the item ID/index, and
returns through the ordinary host-call completion path. Frame-rate requests
join the existing safe-VBlank 30/60 toggle; render-size requests recreate the
host presentation target; widescreen and F8 requests both apply the reversible
cull setting and switch to the paired aspect family. Four resolution values
are exposed through index 3, ending at 1920x1440 / 2560x1440. Accepted runtime
choices are published for main-thread INI persistence. Synthetic object-graph
coverage verifies the fingerprint,
rebinding, labels, values, and all three callbacks. A supported-image
300,000,000-instruction front-end probe loaded the sector overlays and stopped
on its requested budget after 531 VBlanks without a guest fault. The original
invisible-screen behavior and the later logical-name collision are
live-confirmed. Synthetic coverage and a supported-image boot probe pass with
`HostDSP`; selecting Display and the three-row layout still need the final live
visual retest.

### Memory-card BIOS path — verified

The `OL2_REL.BIN` front-end overlay contains the retail memory-card menu and
the bundled Psy-Q `libmcrd` implementation. Its symbols and disassembly expose
both layers of the boundary:

| Retail symbol | Address | BIOS boundary |
| --- | ---: | --- |
| `MemCardReadFile` | `0x80015690` | `open`, `lseek`, `read`, `close` |
| `MemCardWriteFile` | `0x800158B0` | `open`, `lseek`, `write`, `close` |
| `MemCardGetDirentry` | `0x80015AD0` | `strcat`, `firstfile` / `nextfile` |
| `_card_write` | `0x8001A418` | `B0:4E`, one 128-byte frame |
| `_card_read` | `0x8001A428` | `B0:4F`, one 128-byte frame |
| `_new_card` | `0x8001A408` | `B0:50` |

The file boundary is `B0:32` open, `B0:33` lseek, `B0:34` read, `B0:35` write,
`B0:36` close. Retail reaches all five through the thunk block at
`0x800BAD68`..`0x800BADA8`. `A0:15` is `strcat`, not open: `MemCardGetDirentry`
formats `bu00:` at `0x800160CC` and appends the filename pattern with it at
`0x80015B44`, so a host that does not concatenate leaves every scan searching
for the bare device prefix and reporting an empty card.

`MemCardStart` at `0x80014A80` installs callback-mode events for software
class `0xF4000001` and hardware class `0xF0000011`, each with success (`4`),
error (`0x8000`), timeout (`0x100`), and new-card (`0x2000`) specs. Successful
file calls plus `_card_info`/`_card_load` therefore queue the software callback;
raw frame transfers queue the hardware callback. The host delivers these with
`beginInterruptCall`, preserving the existing interrupt-stack rule.

The file `read`/`write` boundary is asynchronous: a zero return accepts the
operation, and retail then waits for the software-card callback. Returning the
transferred byte count causes its tight retry loop to reissue the operation.
An empty `firstfile` scan is another special case: the bundled Psy-Q wrapper
enters `_get_card_event_x`, so the zero-result path must raise a successful
hardware-card event or the fresh-card Save/Load flow waits forever.

`_get_card_event` (`0x80018740`) waits on the four software-class flags at
`0x800DDBFC`..`0x800DDC08`; `_get_card_event_x` (`0x80018818`) waits on the four
hardware-class flags at `0x800DDC0C`..`0x800DDC18`. Both are set only by the
callbacks installed at `0x800183A8` and cleared by the waiter itself.

### The kernel device table is a prerequisite for `firstfile` — verified

Retail does not call `B0:42` directly. It links its own libapi `firstfile` at
`0x800BADB8`, which extracts the device name from the path, walks the kernel
device-control-block table at `0x150`/`0x154` (0x50-byte entries) for `"bu"`,
saves that entry's `firstfile` slot (`+0x34`) to `0x800E2B6C`, replaces it with
its own patch at `0x800BAF54`, and only then issues `B0:42` at `0x800BAF30`.
When the walk finds no `"bu"` device it returns NULL at `0x800BAE90` **without
reaching the BIOS at all**. `MemCardGetDirentry` reads that NULL and blocks in
`_get_card_event_x` on a hardware completion no BIOS call ever raised.

That is the confirmed-save freeze: `guest_pc=0x8001885C`, `guest_ra=0x80015BC0`.
The host therefore publishes a single `"bu"` control block during card device
setup. Only three instructions in the whole image read that table
(`0x800BAE14`, `0x800BAEBC`, `0x800BAF94`), all inside `firstfile` and its
patch, so nothing else observes it. Only the name pointer and the writable
`+0x34` slot are used; every BIOS service still enters through the A0/B0
vectors.

Reproducible headless route to the Save confirmation, from a fresh card:

```bat
... --probe-guest --guest-budget 1500000000 --rasterizer --publication-dump 2600 ^
    --script-input "200:start,1400:start,1420:down,1432:down,1444:down,1456:cross,1500:right,1512:cross"
```

The pause menu is Resume / Quit / Load / Save / Options, so Load is two `down`
presses and Save three; the confirmation defaults to `No` and needs `right`.
With both defects fixed the dump reads "Game file successfully saved", the card
holds a `0x51` directory entry for `BASLUS-0068400` with an `SC` block header,
and dropping the last two presses replays the same route as a Load.

The higher-level memory-card worker is installed separately through
`VSyncCallbacks(7, 0x80016020)`. `VSyncCallback` is only the convenience API
for slot 4; modeling that single slot leaves `WaitForCompletion` spinning
before the first card BIOS call. The host therefore retains all eight callback
slots and schedules every populated slot at each VBlank, in slot order.

This failure was reproduced through the retail pause menu with a fresh card:
the scripted Load route (`200:start,1300:start,1320:down,1332:down,1344:cross`)
spent the rest of a 900,000,000-instruction probe at `0x80014008` inside
`WaitForCompletion`, without reaching a card BIOS call. With slot 7 scheduled,
both that route and the sibling Save selection (one additional `down`) stopped
only on the requested instruction budget in ordinary gameplay code around
`0x80093600`; each scheduled 3,033 VSync callbacks across 1,594 VBlanks.

The backing store is the console's standard 1,024 × 128-byte raw image. A
missing card is formatted with an `MC` header, fifteen free directory frames,
and twenty erased broken-sector entries. Deterministic coverage creates a
one-block retail-style file, writes and reads it through BIOS calls, enumerates
its 40-byte `DIRENTRY`, reads its raw directory frame, reloads the `.mcr`, and
recovers the exact payload. A 500,000,000-instruction title-route probe with
the card attached stopped only on its requested budget, not an unsupported
BIOS boundary.

### The retail 30 Hz update gate — verified

Retail is locked to 30 Hz by three instructions in `VSCallback__Fe`:

```text
0x800A0158  subu  $v0, $v0, $v1     ; rFrameCount60 - lastSwapVBlank
0x800A015C  sltiu $v0, $v0, 2       ; the 30 Hz lock
0x800A0160  bnez  $v0, 0x800A0274   ; too soon: leave the swap pending
```

`QueueSwap__11RenderQueue` registers this callback when a swap is requested,
and the callback refuses to complete one until two VBlanks have passed. The
render queue only frees a layer once a swap completes, so
`WaitForLayer__11RenderQueueUl` stalls the whole game loop. The cadence is not
a performance limit: the live trace measures exactly two VBlanks and exactly
`2 * 564,480` guest instructions between world frames, and `--guest-cpu-scale`
changes neither. `HTickerToGameLoopPercentage__FUl` independently hardcodes a
30 Hz loop period — it scales hblank ticks by `100 / 524.5`, and 524.5 NTSC
hblanks is one thirtieth of a second.

Lowering the bound to one VBlank (`0x2C420002` -> `0x2C420001`) makes the
retail guest run at the emulated display rate. At the console's 60 Hz refresh
that is a real 60 Hz. `frameRate` then reads 60, and the game's own
`__MyFrameRate` latch reports 60. It does not preserve wall-clock speed:
`Step__4Game` calls `Step__4Time` once per game update, and `theTimeMgr`'s tick
counter was measured advancing at 30.13/s unpatched and 60.00/s patched. Retail
advances animation, physics, and gameplay timers per game frame, so unlocking
the gate alone runs gameplay at exactly twice wall-clock speed. `frameRate` is
computed every frame but never read in the main executable, so the engine has
no time-step scalar to compensate with.

### The engine has no time-step scalar — verified

A speed-preserving 60 Hz update would need a per-frame time step the engine
already scales by. It has none.

- `frameRate` is written twice in `EndFrame__7Display` and read nowhere in the
  boot executable, at any LUI search window up to 64 instructions.
- None of the four overlays reads `frameRate`, `debugLockTo30`,
  `__MyFrameRate`, `__MyFrameCounter`, `rFrameCount`, `rFrameCount60`,
  `gameLastFrame`, or `theTimeMgr`. The scan is meaningful: the overlays are
  raw MIPS sharing the boot executable's `$gp`, with plausible `jal`/`lui`
  density, and their gp-relative accesses land in the expected global range.
  A positive control — `0x800DD5B0`, which `BOL_REL.BIN` does use — is found.
- `gameLastFrame` is referenced only by the two `Display` methods that compute
  `frameRate`, so the measured VBlank delta feeds nothing else.
- `HTickerToGameLoopPercentage__FUl` hardcodes the loop period: it scales
  hblank ticks by `100 / 524.5`, and 524.5 NTSC hblanks is one thirtieth of a
  second.
- Motion is integrated inside per-class `Move`/`UpdatePosition` methods
  alongside collision, not through one shared integrator, and the tuning
  globals are per-frame quantities of mixed dimension: `runAccel`,
  `MAX_FALL_SPEED`, `gravityReduction`, `PUSHABLE_GRAVITY`, `poleFriction`,
  `spinRate`, `decayRate`, `THROW_PROJECTILE_VELOCITY`, and many more.
  Velocity-like and acceleration-like constants would need different scale
  factors, so no single blanket adjustment is correct.

`debugLockTo30` is defined but referenced nowhere, which fits a development
build that could run unlocked for profiling while shipping a fixed 30 Hz step.
Unlocking the gate is therefore correct as a cadence change and wrong as a
speed change: retail is a fixed-step 30 Hz engine, and running it at 60 Hz at
correct speed is an engine-wide retiming rather than a patch.

### `DynamicThing` is the shared motion integrator — verified

Located by running `--motion-trace` through real first-level gameplay, then
reading the ranked writer PCs. Every moving entity — player, enemies, objects —
integrates through these two base-class methods, so retiming does not have to
touch each per-class `Move`/`UpdatePosition` override.

`DynamicThing` field map, from the trace offsets plus the disassembly:

| Offset | Meaning | Evidence |
| --- | --- | --- |
| `0x1C`–`0x24` | previous position | written from position at `UpdatePosition+0xA8..0xB0` |
| `0x54` | block number | `UpdatePosition+0x98` |
| `0x58` | flags; bit 4 gates the block lookup, bit 5 suppresses clearing it | `UpdatePosition+0x40`, `+0x94` |
| `0x64`–`0x6C` | secondary accumulator | `Move+0x4E4..0x4E8` |
| `0x70`–`0x78` | velocity, in world units per game frame | read at `Move+0x3C0..0x3E8` |
| `0x7C`–`0x84` | position | `Move+0x3FC`, `+0x41C`, `+0x430`; matches `Move__5Thing` |
| `0x88`–`0x90` | impulse accumulated this frame, zeroed at `Move+0x50C..0x514` | `Move+0x4F0..0x4FC` |
| `0x94`–`0x9C` | previous frame's impulse | `Move+0x4F8..0x500` |
| `0xA0`–`0xA8` | per-frame position delta, derived | `UpdatePosition+0x20..0x54` |

The position integration is `Move__12DynamicThing+0x3BC..0x430`
(`0x800622BC`–`0x800622F4`):

```text
80062280  addu  $a0, $a0, $v0      ; step.x  = scaled motion + velocity.x (0x70)
80062298  ...   $v1, 0x74($s1)     ; step.y += velocity.y
800622AC  ...   $v1, 0x78($s1)     ; step.z += velocity.z
800622BC  lw    $v0, 0x7c($s1)
800622C4  addu  $v0, $v0, $a0      ; position.x += step.x
800622C8  sw    $v0, 0x7c($s1)
800622CC/E0                        ; position.y += step.y
800622E4/F4                        ; position.z += step.z
```

The scaled term above it is a 64-bit fixed-point multiply shifted right 16;
`DYNAMIC_THING_OBSTACLE_VELOCITY_DECAY` (`0x800DD01C`) is loaded through
`$gp + 0x6D0` in the same block. Velocity is added unscaled, confirming it is a
per-game-frame quantity rather than a per-second one.

`UpdatePosition__12DynamicThing` (`0x8006272C`) integrates nothing. It records
`delta = position - previousPosition` into `0xA0`–`0xA8`, optionally refreshes
the block number, then copies position into `0x1C`–`0x24`.

Gravity is in the same function. `Move__12DynamicThing` loads the working
velocity into `0x10`–`0x18($sp)` from the persistent velocity at `0x64`–`0x6C`,
subtracts field `0xC4` from the Y component every frame, clamps against
`MAX_FALL_SPEED` (`0x800DD018`, referenced from exactly this one place), and
writes the result back to `0x68`:

```text
80062124  lw    $a0, 0xc4($s1)
8006212C  beqz  $a0, 0x80062158
80062130  addiu $v0, $zero, 0x12   ; reload, in the branch delay slot
80062134  lw    $v0, 0x14($sp)
80062138  lw    $v1, 0x6cc($gp)    ; MAX_FALL_SPEED
8006213C  subu  $v0, $v0, $a0      ; velocity.y -= gravity
80062150  addiu $v0, $zero, 0x12   ; reload, in the clamp's delay slot
80062158  sw    $v0, 0xc4($s1)     ; gravity is reset to 18 every frame
```

Because the working copy is written back to the persistent velocity, this
accumulates across frames and is a real acceleration rather than a constant
fall speed. `MAX_FALL_SPEED` is a velocity clamp and correctly stays untouched —
velocity keeps its retail per-frame units, which is what makes every other
threshold remain valid.

Field `0xC4` has around fifteen legitimate writers: `Move`'s own reload,
`Reset__12DynamicThing`, many `Player` states (`_Jump`, `_Flip`, `_WallJump`,
`_TableRoll`, `_HorizontalPoleSwing`), several `Humanoid` states
(`_FlyingBack`, `_Floating`, the ladder states, the collision handlers), and
object classes in the disc overlays. Some store zero to disable gravity;
others store a value read from a data struct.

**Retime it at the point of use, not at the writes.** There is exactly one
reader — `0x8006213C` in `Move__12DynamicThing` — so hooking the read covers
every source by construction. Two earlier attempts did the opposite and both
were silently incomplete: patching `Move`'s two immediates left the player's
jump untouched, and adding `_Jump__6Player+0x458` still left launcher pads
untouched. Each looked correct in the situation it was tested in.

The first of those was caught by a jump trajectory trace: with only the
immediates patched, the player's velocity still fell by 19 units per frame in
both the stock and retimed runs, while the retimed peak dropped from 574 to
320 — the position step was halved but nothing had slowed the fall. Sampling
the field's value looked correct; only the trajectory, and then the ranked
writer list, showed otherwise.

The general rule this produced: when retiming a per-frame quantity, count the
writers and the readers before choosing where to patch, and prefer whichever
side is singular.

Collision response adjusts position and velocity afterwards through
`HandleThingFloor__FP12DynamicThinglll`, `HandleThingWall__FP12DynamicThinglll`,
and `HTW_HandleWallCollisions__FP12DynamicThinglll`, which write `0x58`, `0x6C`,
`0x80`, `0x84`, and `0xAC`–`0xB4`.

Halving the position step for a 60 Hz update therefore needs one site, but not
one word: it requires inserting a shift before each of the three `addu`
instructions. That is what `RetailTrampoline` and `--retime-motion` do.

Rounding matters here. Steps are small integers, so truncating the halved step
loses half a unit on every odd step, always downward. Live play identified this
exactly: with a floor, jump speed was correct but jump height was visibly
reduced at both update rates, because the upward half of a jump is a long run
of small decreasing steps whose losses all accumulate the same way. The
trampoline rounds half to even instead. Retail's own halving idiom, visible at
`0x800621E4`–`0x800621EC` as `srl` of the sign bit then `addu` then `sra`,
rounds toward zero — also biased, and not a template to copy for this.

### Animation runs off the master game clock — verified

The player's animation state is not in `Player`. `Player::CreateModel`
allocates a 136-byte `PlayerModel` at `Player+0x50`, and `PlayerModel::SetAnim`
reaches its `AnimStructure` through `PlayerModel+0x20`. Watching that chain
with `--motion-trace` through real gameplay ranked these as the per-frame
writers:

| Offset | Writer | Meaning |
| --- | --- | --- |
| `0x50` | `0x80070E4C` | animation cursor, set from the game clock |
| `0x4C` | `0x800710F0` | the previous frame's cursor |
| `0x3C`, `0x48` | `0x80070EC8`, `0x800710EC` | playback rate, 16.16 fixed point (`0x10000` is 1.0) |

The cursor is not a private counter:

```text
80070E20  lw   $v0, -0x28ec($v0)   ; theTimeMgr (0x800DD714)
80070E40  lw   $v1, 0x1c($v0)      ; its tick counter
80070E4C  sw   $v1, 0x50($s0)      ; animation cursor = game clock
80070E58  subu $v0, $v1, $v0       ; advance by the delta against 0x4C
```

`theTimeMgr`'s tick at `+0x1C` is incremented once per `Game::Step` by
`Step__4Time` (`0x80044A40`), and it is the same counter that measured the
guest update rate at 30.13 against 60.00 ticks per second. Animation, timeouts,
and many state counters therefore read one master clock, and because the
animation advances by a *delta* rather than by a fixed step, halving that
clock's rate is safe: on a skipped tick the delta is simply zero.

It is not, however, the *only* per-frame quantity: an object free to keep a
counter of its own does not have to read the clock. See the tutorial arrows
and standalone fullscreen fades below.

### Fullscreen transition fades use a private counter — verified

The title/start transition is one of four boot-executable loops using the same
fade helpers. `0x8002C9A0` initializes a grayscale byte to zero and its step to
17; `0x8002C9BC` advances and clamps it:

```text
8002C9A0  addiu $v0, $zero, 17
8002C9A4  sb    $zero, 0xd40($gp)  ; grayscale = 0
8002C9A8  sb    $v0, 0xd3c($gp)    ; step = 17
8002C9BC  lbu   $v0, 0xd40($gp)
8002C9C0  lbu   $v1, 0xd3c($gp)
8002C9C8  addu  $v1, $v0, $v1     ; advances once per loop pass
```

The four update call sites are `0x80029E84`, `0x8002BEB4`, `0x8002C11C`, and
`0x8002C2D0`. Their loops render and swap directly; none calls `Step__4Time`.
The title-to-intro loop at `0x8002BEB4` therefore reaches the clamp after 15
guest frames—about 0.25 seconds at a 60 Hz update instead of retail's roughly
0.5 seconds—and can cut short the Start-sound transition.

`retimedFullscreenFade` displaces the step load at `0x8002C9C0` and substitutes
zero for the step on every call but the first of each authored step. It owns an
accumulator at `0x80003384`, separate from the game clock's, and resets it when
the loaded grayscale is zero. The reset seeds it one short of the divisor, so a
fade's first call always advances and retail's first visible shade is preserved
at any rate. An executable test runs the complete retail helper and proves the
retimed trajectory matches the 15-call 30 Hz trajectory at equal elapsed times
for divisors one through four.

### One retail game step costs about 316,000 instructions — measured

Measured on the title-to-first-level route by reading `theTimeMgr`'s tick
counter against the guest VBlank counter over the last 300 rasterizer
publications, with `--retime-motion --retime-clock` and the clock divisor
matching the update rate. Authored ticks per wall-clock second, which should be
30 at every rate:

| Update rate | `--guest-cpu-scale` | Authored ticks/s |
| --- | --- | --- |
| 60 | 1 | 29.90 |
| 90 | 1 | 30.10 |
| 120 | 1 | 26.89 |
| 120 | 2 | 30.10 |
| 240 | 1 | 13.65 |
| 240 | 3 | 29.70 |

The shortfalls are not a retiming error. The guest CPU executes
`33,868,800 / vblank_rate` instructions per emulated VBlank, so at 240 Hz a
refresh buys 141,120 — less than half a game step. `WaitForLayer` absorbs the
difference and the whole simulation, still internally consistent and
deterministic, advances in slow motion. Dividing the sustained rate into the
CPU rate gives roughly 316,000 instructions per game step, and the scale that
first restores 30 ticks/s at each rate matches
`ceil(update_rate * 316000 / 33868800)` exactly.

This is one route on the bootstrap one-instruction-per-cycle model. A heavier
scene costs more, and a cycle-aware scheduler will change the constant.

### The host has 1.10x real-time headroom — measured - outdated

A host-side measurement, not a guest one, but it bounds every guest-cadence
decision. Timing `--probe-guest --guest-budget 600000000 --rasterizer` on the
development machine gave 16.10 s, or 37.3M guest instructions a second, against
the console's 33.87M. The probe runs unpaced, so this is the interpreter's
ceiling; live play also carries the presenter and OpenAL on the main thread.

The consequence is that `--guest-cpu-scale` is not usable above one in live
play. It multiplies the instructions the host must deliver per wall-clock
second, so scale two demands 67.7M against an available 37.3M and the guest
runs at about 0.55x real time. Both audio and gameplay slow, because audio is
produced per guest VBlank and the VBlank boundary is the instruction counter.

Follow-up measurement on the heavier 60 Hz retimed quick-save repro
(`quick-save-20260808-180517-708.stsm`, fixed 100M-instruction headless probe)
found a regression-era baseline of 3.255 s / 30.7M instructions/s. Enabling
whole-program optimization for the core and app, indexing the active retime
hooks instead of binary-searching them per instruction, and polling the
quick-save atomic every 64K instructions reduced the same deterministic probe
to 2.614 s / 38.3M instructions/s including process startup and diagnostics:
24.5% higher throughput, with the same final PC and device counters. Capturing
stdout rather than printing it measured 2.540 s / 39.4M instructions/s. This is
a headless ceiling; the supplied `start.ps1` route was subsequently
live-confirmed nearly locked at 100% in the reported heavy position.

A second-stage cleanup removed the remaining 64K-instruction mask check from
the interpreter loop. F5/F6/F9 already publish one atomic request from the main
thread; the guest worker now consumes it immediately before an owed VBlank,
where the machine is at a deterministic safe point. A successful load restarts
the loop so the restored scheduler cannot receive an extra VBlank from the
abandoned timeline. The captured-output probe fell from 2.540 s to 2.448 s /
40.8M instructions/s, another 3.8%, with the same PC and device counters.

That also gives a clean discriminator for bug reports: a retiming fault cannot
slow audio, because audio production never passes through a retiming patch. If
sound is slow too, the guest is not keeping up with wall clock and the schedule
is innocent.

### The tutorial arrows bob on a counter of their own — verified

`Think__5Arrow` (`0x8001BBD8`, in `NBOL_REL.BIN`) offsets the arrow along its
normal by `t * t` and steps `t` once per call, wrapping -7 to 7:

```text
8001BCB0  lw    $s1, 0x74($s2)
8001BCB8  mult  $s1, $s1          ; the parabola
8001BDA4  lw    $v0, 0x74($s2)
8001BDAC  addiu $v0, $v0, 1       ; once per Think, not once per clock tick
8001BDB4  slti  $v0, $v0, 8
8001BDBC  addiu $v0, $zero, -7
```

That is why retiming only the master clock left the arrows at double rate at 60
Hz while clock-driven animation and timers came out right. `--retime-clock`
now adds the frame parity instead of one, so the fifteen-step cycle keeps its
wall-clock length.

The site is in an overlay, which is the first patch here that is. Overlay code
is replaced on level transitions and two of the four overlays share each load
address, so the patch is fingerprinted by an eight-word window rather than one
word and re-applied whenever that window reappears unpatched. The window occurs
exactly once across all four `*_REL.BIN` overlays, which also confirms the
`NBOL_REL.BIN` pairing independently of the symbol table.

### Scene and VRAM animation boundaries — verified

Retiming `theTimeMgr` does not cover two independent animation boundaries in
the boot executable. They must be bounded separately at a 60 Hz game update.

`Step__4Game` advances the master clock and then immediately advances four
general scene-animation lists:

```text
8002B6C8  jal   0x80044A40        ; Step__4Time
8002B6D0  jal   0x8002B368        ; animLoopDSTACK
...
8002B398/3A8/3B8/3C8
          jal   0x8002B290        ; AnimateLoop, four Director lists
```

Each list invokes the animation object's update virtual once. This covers the
authored transform/vertex/visibility timelines used by background scenery; it
does not read `theTimeMgr`.

VRAM flipbooks have a separate singular update during rendering:

```text
8002AD90  jal   0x8003BB90        ; Director::updateVramAnims
8003BBB0  jal   0x8008D3C4        ; tFlipbook::AdvanceFrame (Director+0xC8)
8003BBC8  jal   0x8008D3C4        ; tFlipbook::AdvanceFrame (Director+0xD0)
```

`--retime-clock` gates both singular call sites on the hold decision that
`retimedGameClock` publishes into host `RetimeState`. One holds the call
and zero executes it, so all three timelines advance on the same 30 ticks per
second at any guest update rate. The sites and call targets are exact-SYM plus
disassembly evidence. Executable tests exercise the gate hooks and prove
three advances over six alternating decisions.

The level-one entrance neon is not owned by either boundary. A scanout-crop
time series showed the actual failure: stock transitions alternate after 32
and 38 VBlanks, while retimed 60 Hz initially alternated after 16 and 19. The
two changing glow quads were traced backward through `tDynGeom` and `tETree` to
a `tVizFlip`; its absolute frame is selected by `tCompositeFlip`, written by
`ComEffect::SetFrame`, and supplied from `WEffect::Display`. The owner is
`WEffect::Update`:

```text
8008BB2C  lhu   $v0, 0x4c($s1)    ; authored sub-frame counter
8008BB34  addiu $v1, $v0, 1
8008BB3C  sh    $v1, 0x4c($s1)
...
8008BB5C  addiu $v0, $v0, 1       ; advance effect frame
8008BB6C  sh    $v0, 0x48($s1)
```

Gating a child `tVizFlip` or `tCompositeFlip` is wrong because those functions
apply an absolute frame that `WEffect` has already advanced. `--retime-clock`
instead gates `Update__7WEffect` at `0x8008BA2C`, after its stack allocation
and saved `$s1`. On a held tick the host hook restores the saved callee
register, unwinds the frame and returns. On a counted tick it reproduces the
displaced `move $s1,$a0` and resumes at `0x8008BA34`. After this hook the
60 Hz crop alternates after 32/38 VBlanks, exactly matching stock. This
boundary also retimes world-effect motion, the path used by moving
environmental effects.

`FWEffect` is a separate case: its `Update__8FWEffect` override never calls
`WEffect::Update`. It owns another `+0x4c` sub-frame counter, `+0x48` frame
counter, and movement integration. The gate at `0x8008C484` therefore applies
the same parity directly to that override. Treating this as the first-level
traffic path was an incorrect hypothesis: the gate is still required for
flying world effects, but it does not own those cars.

The exact level data resolves the traffic owner. `LEV01.LCF` contains object
`carA`, model `merce`, path `path1`, with class property `0xc9`. `AI::Populate`
passes that class to the object factory, whose `0xc9` branch constructs a
`Platform` (`Platform::Platform` at `0x80020844`). Its path is advanced by
`Platform::Move` at `0x80022788` in `NBOL_REL.BIN`, independently of the shared
`DynamicThing` position integrator and the world-effect updates. The overlay
patch gates the safe prologue site at `0x80022790` with the master-clock parity;
its twelve-word fingerprint occurs only once across all four gameplay overlays.

### Obstacle objects own a whole authored timeline in `Think` — verified statically

`Platform::Move` is only the path advance. The dispatched update is
`Think__8Platform` (`0x80021918`, `NBOL_REL.BIN`), reached once per game update
from `AI::privMoveList` (`0x800553DC`) through vtable slot `+0x14`
(`__vt_8Platform` at `0x80025F08`; slot `+0x10` is `Move` at `0x80022788`,
which confirms the existing patch's dispatch path). Around the move call,
`Think` also owns:

- the detached integrator `pos.y += dy; dy -= gravity * 3 / 2`, which a
  breaking platform runs after it gives way — displacement therefore grows as
  the square of the update rate, not linearly;
- `Platform::Bob` (`0x80023190`), `Platform::Teeter` (`0x80022B90`), and
  `Platform::OnXorZRot` (`0x800222F4`);
- the `+0x94` and `+0x98` frame counters that delay a restart or a move;
- `Platform::MovePassengers` (`0x8002337C`), which adds the platform's frame
  delta `+0xA0..+0xA8` to every rider's position, and the `+0xAC..+0xB4`
  snapshot `Platform::GetDeltaVelocity` publishes.

`Think__8Pushable` (`0x80017FAC`, `OL1_REL.BIN`) is the same shape.
`Pushable::Move` (`0x8001811C`) integrates position from velocity `+0x80/+0x88`
and then decays that velocity by the friction terms `+0x8C/+0x94`, all per
call, so a shoved object travels about `k` times as far per authored step and
stops in about `1/k` of the time.

Why that drops the player rather than only looking wrong:
`Obstacle::HandleHumanoidObstacleCollision` (`0x8007C178`) calls
`DynamicThing::Disembark` (`0x800624C4`) near the top of every update, runs the
obstacle pass — each candidate's `HandleHumanoidCollision`, vtable `+0x54` —
and then compares `DynamicThing::GetTicketIssuer` (`0x80062550`) before and
after:

```text
8007C650  jal   0x8006C42C        ; Humanoid::LetGoOfLedge
```

That call is reached when the humanoid held a ticket at entry and no obstacle
re-issued one during the pass. An obstacle that moves a full authored step
while the retimed player moves `1/k` of one fails
`CheckXZStaticBoxCylinderCollision` (`0x8007A740`), so the mantle disengages on
the update it started.

`--retime-clock` therefore holds both `Think` prologues on the published
decision, at `0x80021920` and `0x80017FB4`. Both twelve-word fingerprints
occur exactly once across the four gameplay overlay files. Collision handling
is unaffected because the collision manager calls `HandleHumanoidCollision`
directly rather than through `Think`, so tickets keep being issued every guest
update.

Observed overlay residency on the headless title-to-level-one route:
`NBOL_REL.BIN` occupies the second slot and `OL2_REL.BIN` — not
`OL1_REL.BIN` — occupies `0x80010000`, so `pushable_think` reports absent
there. The two slots are `[0x80010000, 0x8001A758)` for `OL1`/`OL2` and
`[0x8001A758, 0x8002601C)` for `BOL`/`NBOL`. `overlay_retiming_live=` on stderr
and `OBJ n OF m` in `--debug-overlay` report which patches are installed, and
print the observed first fingerprint word when one is not.

Confidence: the call graph, vtable slots, field offsets, and fingerprint
uniqueness are verified against the retail overlay files. The causal link from
a specific reported mantle failure to this path is inferred from that
structure and awaits live confirmation.

### Every other obstacle `Think` takes the same hold — verified statically

The same treatment generalizes to the whole obstacle set, from one table in
`src/stuntmaster/game/retail_patch.cpp` (`retimedObstacleThinks`,
`retimedBootObstacleThinks`). Symbols come from `GAME_REL.SYM`; every window
below was read out of the extracted image and occurs exactly once across
`BOL`/`NBOL`/`OL1`/`OL2_REL.BIN` and the boot executable together.

The site is normally the prologue's `move $sX, $a0`. By then the frame exists
and `$sX` is stored, and `$ra` is still the caller's, so a held update restores
what the prologue already clobbered, unwinds, and returns without entering the
body.

Two delay slots decide whether a site is usable, and both produced a real
defect before the rule was written down:

- **Retail's instruction after the site** runs as the injected jump's delay
  slot, *ahead of the body*, on both paths. It must not write `$sp`, `$ra`, or
  any operand the displaced instruction still has to read. `Door` breaks this
  at the `move`: its delay slot is `lui $a0, 0x800e`, so the displaced
  `move $s0, $a0` received a destroyed `$a0` and every counted update ran
  `Think` on `0x800E0000`. Observed live as doors that never unlock — no
  `DeathCheck`, so no lightbulb — and no opening animation on the ones already
  unlocked, because the virtual `Move` in the `case 4` arm was never reached
  either. `Door`'s site is therefore two words later, at the `lw` whose delay
  slot is `sw $ra, 0x24($sp)`.
- **The body's own branch delay slot** carries the displaced instruction, so
  that runs on the held path too. The restores must stay off the counted path:
  `Door`'s `move $s0, $a0` executes *before* its site, so reloading `$s0` on a
  counted update would replace the door with the caller's `$s0` — the same bug
  a second time. Putting a restore there also creates a load-delay hazard with
  a displaced `move` into the same register.

`holdIsWellFormed` in `retail_patch.cpp` is a `static_assert` over both rules
plus the frame size and the restore/store pairing, so a descriptor that breaks
either one does not compile.

### The player's pole swing holds its timeline, not its pose-apply — fixed

User report: on a horizontal pole at 60 Hz the player swings twice as fast and
the model flickers between the arc position and a slowly sinking one (repro
`saves/debug-swinging.stsm`). Both symptoms have the same root: the whole
state function runs once per guest update, and the pendulum step couples its
accumulators with its apply in registers.

`_HorizontalPoleSwing__6Player` (`0x80032F8C`) computes, in one pass:

- `Player+0x1A8` is the swing angular velocity (`field424` in the ReChan port
  of `PLAYER.CPP:3802`). The torque-scaled delta is accumulated per call and
  stored at `0x800330DC` (`sw $a0, 0x1a8($s1)`).
- `Player+0x28` (orientation.x) is the swing angle: `newAngleX =
  angleX + ((2182 * field424) >> 16)` wrapped mod `0x10000`, stored at
  `0x80033254`.
- The arc position (`Player+0x1C`) and orientation stores at
  `0x80033248`-`0x8003328C` are computed from the new angle in registers
  within the same call.

A counter-level hold cannot freeze this (the angle and position derive from
each other in registers mid-call), and a whole-body hold fails differently:
the body's tail (`0x80033114` onward) is an *idempotent pose-apply* — the
rotation matrix at `Player+0x128`, the arc position and orientation stores,
the gravity zeroing at `0x800332A4`, the FWD/BACK anim switch, the swing
sound, and the dismount checks — that retail runs every step. A whole-body
hold skips it on held updates, so the model rubberbands between the applied
and unapplied poses, and Move's per-update integration (which re-arms the
`+0xC4` gravity field to 18 and steps the position) stands between the
counted updates and sinks the player. That is exactly the `Stack` tumble bug
(`9bd6a03`): the fix must hold the timeline while the idempotent pose-apply
runs every update.

Fix (landed): `pole_swing_timeline`, a gate at `0x80033078` — the velocity
read `lw $v1, 0x1a8($s1)` that starts the accumulation. A counted update
models the displaced load and resumes at `0x80033080`; a held update jumps to
`0x80033114`, the angle-fraction section that begins the pose-apply, so the
velocity and angle stay at the previous authored step while the apply re-runs
every update and keeps overwriting the position — and zeroing gravity, so
Move reads no fall term and the stored velocity stays constant. Nothing the
apply reads comes from the skipped region: the pole anchor (`$s2`), saved
position (`$s3`), and angles (`0x18`-`0x20($sp)`) are set before the site,
and the apply reloads `$v1`/`$a0`-`$a3` itself. The flip-dismount counter
(`player_pole_swing_timer` at `0x800331B4`) now matters more than ever: its
site lives inside the apply, so it runs every update and the counter hook
holds it on held updates.

Measured A/B on `debug-swinging.stsm` at 60 Hz, same `--guest-budget`, via
`--motion-trace`: the swing velocity store (`store_pc` `0x800330DC`, offset
`0x1A8`) drops from 106 writes per run (unfixed) to 53 — the authored
half-rate, with the value still varying (the swing drives). The pose-apply
stores (`+0x28`, `+0x1C`, and the `+0xC4` zeroing) all count 106 — every
update — and the per-frame samples show each arc position for two consecutive
samples with `vy` constant at zero: no alternation, no sink.

Confidence: static (disassembly plus the ReChan typed port, cross-checked
against the `Stack` precedent) and the deterministic write-count A/B; live
visual confirmation is open on the repro save.

### Ladder contact and climb cadence need narrower hooks

`Ladder::Think` (`0x80089FD4`) owns only the ladder object's death/trigger
timeline, so its held prologue remains correct. Player attachment and climbing
live elsewhere. `Ladder::HandleHumanoidCollision` (`0x8008A260`) sets contact
bit `Humanoid+0x170:1`; `_LadderLatch` (`0x80069C2C`) and `_ClimbLadder`
(`0x80069CF8`) consume that bit on the following update. Retail clears the bit
every update. Gating the whole obstacle collision pass therefore made a held
update clear it without refreshing it, and the next ladder-state call kept
reinitializing action `0x1c` and its animation instead of climbing.

`obstacleCollisionPassHook` now invokes the same per-humanoid inner collision
routine (`0x8007C178`) on held updates for ladder actions `0x19` through
`0x1c`, just as it already does for an active pusher and a jumping passenger.
All other humanoids and obstacle ticket/carry work remain authored-rate gated.

Two direct operations in `_ClimbLadder` also bypass the shared retimed readers:

- upward climbing calls `IncFrame__13AnimStructure` at `0x80069F08`; the
  `ladder_climb_up` gate runs that call and its following footstep test only on
  the published authored update, jumping to the epilogue at `0x80069FD4` when
  held;
- downward sliding uses `addiu $v0,$v0,-0x40` at `0x80069FC8` and stores it in
  the delay slot at `0x80069FCC`; `ladder_slide_down` replaces that already-run
  store with `-0x40 / divisor` (half-to-even), leaving both `$v0` and position
  Y consistent.

The supplied quick saves make this deterministic. Repeating simultaneous
`up`/`circle` from saved VBlank 4125 (retail) and 4266 (60 Hz retime) produces
the same authored sequence: latch position `Y=-8447`, root-motion transition
to `-8017`, climb samples through `-7467`, then the top dismount. The 60 Hz
trace repeats each climb sample once between advances. Before the fix it
entered action `0x1c` but stayed at `Y=-8449`; with contact alone repaired it
climbed, but advanced every guest update and was twice retail speed.

`obstacleCollisionGateServicesContactsThatCannotWait` covers all four ladder
states. `ladderStateHooksKeepAuthoredCadence` covers counted/held ascent calls,
the real ascent delay slot, and descent deltas at divisors 1, 2, and 4.

Confidence: verified against boot-executable disassembly, the reconstructed
Ladder/Humanoid bodies, focused hook tests, and the deterministic retail versus
60 Hz quick-save motion traces.

### `Stack` cannot be a whole-`Think` hold — it needs two gates

`Stack` is the one obstacle removed from the table above. A punched stack of
boxes topples and leaves its bottom box as a `Pushable`. `Think__5Stack`
(`0x8001EE28`, `NBOL`) is not a pure timeline: it re-poses a display model from
a tumble animation on **every** call, and the intact stack is that model's rest
pose. At a high guest update rate the scene is rebuilt every update, so holding
the whole `Think` skips the pose-apply on the held updates and the model snaps
back to its rest pose — the stack rubberbands between its toppling frame and its
intact frame at the guest rate. Its layout, confirmed by disassembly:

```
8001EE44  lw   $a0, 0x88($s1)   ; tumble state         <- timeline gate site
8001EE4C  ...                    ; 1 -> Wobble, 2 -> Fall, 3 -> epilogue
8001EE74  jal  Wobble__5Stack    ; owns the 0x98 fall counter and transitions
8001EE84  jal  Fall__5Stack      ; counts 0x98 to 0x2a, then FinishStack
8001EE8C  ...                    ; s0 = (stack->0x8c AnimStructure)->0x1c
8001EE9C  jalr vtbl[0x18](0x98)  ; set the animation frame from the counter
8001EEB4  jalr vtbl[0x14]()      ; commit the pose            } pose-apply,
8001EEBC  lw   $a0, 0x9c($s1)    ; CKnockDownSound  <- sound gate site  } every
8001EECC  jal  Think__15CKnockDownSound (0x800AD4AC)          } update
```

`Wobble`/`Fall` own the authored 30 Hz timeline (the `0x98` counter, the state
transitions, and — from `Fall` at `0x2a` — `FinishStack`, which spawns the
`Pushable`). The pose-apply (`vtbl[0x18]`/`vtbl[0x14]`) is idempotent given the
counter and must run every update. The tail's `Think__15CKnockDownSound`
decrements two frame countdown timers (`0x1c`/`0x1e`) per call, so it is
rate-sensitive like the timeline.

So `Stack` is retimed by two narrow control-flow gates, `retimedStackTimeline`
and `retimedStackSound`, rather than a whole-`Think` hold:

- **`stack_timeline`** (site `0x8001EE44`, arena `+0x240`) squashes the tumble
  state to `0` on a held update, unless it is already the finished state `3`.
  State `0` routes the dispatch straight to the pose-apply, so `Wobble`/`Fall`
  are skipped on held updates while the pose still runs; state `3` still routes
  to the epilogue, so a finished stack is not re-posed. Its fingerprint window is
  the same twelve-word `Think` prologue the old whole hold used.
- **`stack_sound`** (site `0x8001EEBC`, arena `+0x280`) nulls the sound pointer
  on a held update so retail's own `beqz` skips `Think__15CKnockDownSound`,
  keeping its countdowns on the authored schedule. Its window is the twelve-word
  pose-apply-and-sound tail from `0x8001EEA4`; both windows read back exactly
  once across the four `*_REL.BIN` files, and neither covers the other's site.

Both gates use `$at` and deliberately set `$a0` (the value being squashed);
each site's delay slot (`lw $s0, 0x1c($v0)` and a `nop`) is safe before the body
on both paths. `stackGatesRedirectOnlyOnAHeldUpdate` in `core_tests.cpp` runs
each gate against the real prologue bytes and checks the redirect fires only on
a held update, per state, plus fingerprint reversibility.

The nineteen bodies share one arena block at offset `0xC20`, stride `0x30`.
It starts there rather than at `0xC00` because `obstacle_overlap_gate` at
`0xBC0` is nineteen words long and ends at `0xC0C`.
`everyTrampolineFitsThePatchArenaTogether` installs every patch into one
runtime and is what proves the layout.

Confidence: prologue shapes, frame sizes, restore slots, and fingerprint
uniqueness are verified against the extracted images.
`everyObstacleThinkHoldReturnsThroughItsOwnPrologue` runs each hold against the
retail prologue it was cut from. It checks that a held update reaches no body
and returns with the stack and `$s0`-`$s3` untouched, and — the check that
would have caught `Door` — compares the whole register file at the rejoin
instruction between a stock run and a counted patched run, `$at` excluded. A
counted update has to be indistinguishable from retail there. The eight `NBOL`
entries
and both boot entries are confirmed installing on the live level-one route; the
nine `OL1` entries await a level that loads `OL1_REL.BIN`, and none of the
nineteen has live behavioural confirmation yet.

### `rFrameCount60` is a VBlank wall clock, and a third retiming category

`rFrameCount60` at `0x800DD678` is incremented once per VBlank by `MyVBL__Fe`
(`0x8002617C`) and by nothing else outside `main`'s initialization. Retail
treats it as wall clock in sixtieths of a second: `MyVBL__Fe` divides it by 60
with the usual magic multiply (`0x88888889`, `mfhi`, `srl 5`) and publishes a
per-second value at `gp+0xD10` whenever the remainder is zero.

How much this matters depends on the schedule, and the answer is not the
retiming divisor. `guestScheduleFor` keeps `vblank_rate` at 60 for any update
rate up to the console refresh and shortens the swap gate instead, so **at 30
and 60 Hz this counter still advances exactly 60 times a guest second and every
duration measured in it is correct**. Only above 60 Hz does the display itself
run faster, and then durations are short by `vblank_rate / 60` — 2 at 120 Hz,
4 at 240 Hz, and a non-integer 1.5 at 90 Hz, which any fix has to handle.

So this is a real defect above 60 Hz and a genuine third category alongside
authored 30 Hz timelines and motion, but it is **not** an explanation for
anything observed at 60 Hz.

**It must not be retimed at its writer.** `VSCallback__Fe` (`0x800A0140`) is
retail's swap gate and is built directly on it:

```c
if (1 < (uint)(rFrameCount60 - iRam00000AD0)) { iRam00000AD0 = rFrameCount60; ... }
```

That comparison is what `thirtyHertzSwapGate` patches to unlock a faster game
loop. Holding the increment would slow the loop back down and undo
high-frequency mode outright. The counter has to keep ticking per emulated
VBlank; its wall-clock *consumers* are what need scaling, one site at a time.

Known consumers, none yet corrected:

| Site | Use |
| --- | --- |
| `UpdateTimeOut__FUlPC10tagLVector5Queue`, `addu $a1, $a1, $a3` at **0x8004485C** | dialog deadline, `rFrameCount60 + window` |
| `rCDWaitUntilDone` (`0x8007F238`) | CD completion timeout |
| `gSyncLoadGroup__Fi` (`0x800944B4`) | load synchronization |
| `MenuFade__Fv` (`0x80029E58`, `0x80029EC8`) | menu fade duration |
| `gsTitleLoopState__4Game` (`0x8002BEFC`, `0x8002C164`) | title loop timing |

A scaling patch has to read a word of its own rather than
`retime_divisor_address`: the divisor counts guest updates per authored 30 Hz
step, which is 2 at 60 Hz where the VBlank multiple is 1. The two are never the
same quantity, and above 60 Hz the multiple is not always an integer.

**Rejected hypothesis, recorded so it is not retried.** The dialog deadline was
suspected of causing voice quips to stop playing at `--guest-update-rate 60`.
It was not. At 60 Hz `vblank_rate` is still 60, so no window is shortened; a
patch scaling `0x8004485C` was written and backed out unbuilt. The reported
symptom turned out not to be a regression at all — see the one-shot dialog
section below.

Confidence: the counter's single writer, the per-second division, the swap-gate
dependency, and the dialog kill path are verified statically. That the skew
exists above 60 Hz follows from `guestScheduleFor`. Nothing here is tied to an
observed symptom.

### Voice quips are one-shot, and look like a regression when they run out

`PlayLoaded__FPC10tagLVector5State` (`0x800440E4`) refuses a line and kills the
dialog under two conditions:

```c
uVar1 = GetHeader__FUlUi(DAT_800d8818, 1);
if ((sRam000004da == DAT_800d8818) || ((uVar1 & 0x80) != 0)) {
    jcsKillDialogByHandle__Fl(DAT_800d8808);
} else {
    ... rsdVoiceOn, UpdateState ...
    MarkAsUsed__FUs(DAT_800d8818);      // sets bit 0x80 in the line's header
    sRam000004da = DAT_800d8818;        // and remembers it as the last played
}
```

`MarkAsUsed__FUs` (`0x80043F30`) reads the line's header byte from the table at
`iRam000004B0` and writes it back with bit `0x80` set. So **each line plays
once** and is then suppressed until that header table is reloaded, and a line
never plays twice in a row regardless.

This matters for debugging because a long session, or repeated play through the
same section, exhausts the available lines and looks exactly like "voice quips
stopped working". It was reported as a 60 Hz regression, survived a three-way
build bisect across `4c77581`, `c5f7f1f` and the obstacle-`Think` work — all
three played quips on a later run — and was never a code defect. **Before
treating silent dialogue as a regression, restart and reach the trigger on a
fresh boot.**

Related state worth knowing: `$gp` is `0x800DC94C` (set at the entry point,
`lui $gp, 0x800e; addiu $gp, $gp, -0x36b4`), so `DlgStatus` is `$gp+0x4D4` =
`0x800DCE20`. The dialog queue is at `0x800D8804`, stride 32: `+0x04` handle,
`+0x0C` deadline, `+0x10` position, `+0x14` sample id. `--watch-writes
800d8804 800d8824` reports queue activity, and shows none on the headless
title-to-level-one route — no quip is triggered there.

### Converting `Platform` from held to divided — implemented as host hooks

Update 2026-08-08: the divide-based conversion is **implemented** on the
host-hook table (not the byte trampolines). `Think` runs every guest update and
the rate-sensitive quantities below are sub-stepped by per-site hooks in
`retimeOverlayHooks()` (`retime_hooks.cpp`), verified against the Ghidra
decompilation. The exact hook sites: `Move` speed `retimedPlatformMoveSpeed`
(`0x800227D0`); `Teeter` mass ×k (`0x80022DFC`/`0x80022E88`), angular-velocity
÷k (`0x80022F48`/`0x80022FA4`), damping `0x11EB` ÷k (`0x80022FFC`);
detached-gravity fall exact phase partitions (`0x80021BDC`/`0x80021C08`);
frame-counter holds `0x94` (`0x80021A94`/`0x80021D38`) and `0x98`
(`0x80021AA8`); `Bob` hold (`0x80021DA8`); held bobbed-Y preservation inside
`Move` (`0x80022814`). `OnXorZRot` needs no hook (it recomputes the box from
the sub-stepped tilt angles every call).

The finding that motivated re-doing this: the byte-trampoline reshape only
sub-steps translation and *holds* `Teeter`, so it never fixed the teetering
car-lift; the divide-based model sub-steps the tilt too. The hooks are
arithmetic-tested only (no byte oracle), and the physics feel still needs live
validation. The reshape byte trampoline is deleted; the app runs the
divide-based hooks. The original (pre-implementation) analysis follows.

The remaining 60 Hz ledge failure is a teetering `Platform` (the car on the car
lift). Cause: `retimedPlatformThink` *holds* the whole update, so the platform
stands still on skipped updates and moves a whole authored frame on the counted
one, while the humanoid moves a k-th per update. `CorrectThingPosition` works in
the obstacle's frame — `humanoidY - obstacleY` for both the previous and current
positions — so on the update a teetering platform swings downward by W the
humanoid's relative sink is `4 - W` where retail's is `11 - W`. Between those
two values retail clears the vertical gate and 60 Hz does not.

Holding is correct for anything nothing else interacts with; it is wrong for an
obstacle a retimed humanoid is standing on or hanging from, because the two step
sizes must match. The fix is to divide `Platform` motion instead, so every
update advances a k-th like the humanoid does. It must be done in one pass:
a partial conversion regresses the level-three moving car and the level-three
cutscene car, both of which the hold currently makes correct.

Quantities to divide, all in `NBOL_REL.BIN` unless noted:

| Site | Quantity | Note |
| --- | --- | --- |
| `Platform::Move`, the `0xB8` speed passed to `Path::Move` | path advance per update | The delta `0xA0..0xA8` and its `0xAC..0xB4` snapshot then scale automatically, so `MovePassengers` carries riders correctly with no further patch. The `0xB8` clamp on the delta divides with it. |
| `Platform::Teeter`, both `/ mass` torque terms reading `0x34` | angular acceleration | Multiply the mass read by the divisor rather than dividing the torque; it is one quantity read twice. |
| `Platform::Teeter`, `local_70/local_68 += angular velocity` | angle integration | `(300)+0xC` and `(300)+0x14`. |
| `Platform::Teeter`, the `0x11EB` damping constant at **NBOL 0x80022FFC** (`li $v1, 0x11eb`, word 0x240311EB) | per-frame damping | One site covers both axes: $v1 is loaded once and feeds the `mult` at 0x80023004 (X) and 0x8002301C (Z). Dividing the constant is a first-order approximation of `(1-d)^(1/k)`; exact would need a per-object remainder. |
| `Platform::Think`, `0x94` and `0x98` | frame counters | Hold these rather than divide — they are counts, not motion. |
| `Platform::Think` falling branch, `0xA4 -= gravity*3/2` and the position add | detached-platform gravity | Same shape as `Move__12DynamicThing`: divide the acceleration and the step. |
| `Platform::Bob`, `Platform::OnXorZRot` | per-frame animation | Divide their steps, or hold them; they do not interact with humanoid collision. |

The `Think` hold must also change shape rather than simply disappearing: on a
skipped update it has to still run `Teeter` (replicating retail's
`0x74` bit 0x13 set / bit 1 clear gate) before unwinding, or the tilt integrates
only once per authored frame and the divide makes it k times too slow. `$a0` is
still the platform at the prologue site and `$ra` is already saved at
`0x58($sp)` by the site's delay slot, so the held path can `jal` and reload it.

`retimedPlatformThink` and `retimedPlatformMotion` were deleted with the byte
trampolines; retest both level-three cars plus the car-lift ledge against the
divide-based hooks.

Before starting, read the hook scratch-register rule in `docs/HANDOFF.md`.
Two sample points in this investigation broke ledge attachment outright by using
`$t2`/`$t3`, which the MIPS ABI permits and retail does not.

#### Deeper reading of the two live level-three symptoms — 2026-08-07

A follow-up session read the whole `Think`/collision path out of the code to
pin two *live-observed* level-three symptoms a player reported at 60 Hz with
`--retime-clock --retime-motion`: (1) the car on the car lift is an unmantleable
detach/attach loop, and (2) standing on the moving car slides the player off
toward the car's direction of travel "after a second," as if the car's velocity
were applied twice. Findings, all read statically and confirmed against the
extracted overlay/boot bytes:

- **Symptom 1 is the teetering-`Platform` ledge loss already recorded above.**
  It is a *real* ticket loss on the counted update, not just a mis-timed one:
  the relative sink is `4 - W` vs retail's `11 - W`, so
  `retimedLedgeTicketDrop` (which only moves *when* the drop is decided) cannot
  fix it. Only the held→divided conversion can.

- **Symptom 2 has a distinct, newly-identified doubler.** The disembark tail of
  `Obstacle::HandleHumanoidObstacleCollision` is
  `GetDeltaVelocity (0x8007C62C) → SetCarried (0x8007C648) →
  LetGoOfLedge (0x8007C650)`. `SetCarried` (`0x80061CC4`, its only caller is
  `0x8007C648`) writes the obstacle's per-frame velocity into the rider's
  carried triple `0x70/74/78`. `retimedLedgeTicketDrop` gates **only** the
  `LetGoOfLedge` at `0x8007C650`; the `SetCarried` at `0x8007C648` is
  **ungated**. So on a skipped-update spurious ticket loss the rider is not let
  go (correct) but its carried velocity is slammed to the car's velocity anyway.
  `Move__12DynamicThing` then folds that carried velocity into position every
  update (`0x80062280`+, divided by `retimedPositionStep` so the *distance* is
  right) **on top of** `MovePassengers` already carrying the rider by the frame
  delta `0xA0..0xA8` — the car's velocity is applied twice, so the rider drifts
  forward and slides off. `MovePassengers`'s own carried-velocity *clear*
  (`0x80061C78`, taken when the rider rests, `vel.y<=0`) cannot compensate
  because it lives inside the held `Think` and only runs on the counted update.
  The held→divided conversion removes the spurious ticket loss and therefore
  removes this doubler with no separate patch. A defensive `SetCarried` gate is
  possible but its natural site `0x8007C648` collides with the diagnostic
  `ledgeTraceLetGoFromTicket`; the clean gate point is the branch
  `0x8007C624` (`bne $s0,$zero,0x8007C660`), forcing the ticket-present path on
  a held update, which defers the *whole* disembark and subsumes
  `retimedLedgeTicketDrop`.

- **`Think__8Platform` (`0x80021918`) is a state machine, not a motion
  routine.** Call map: `Move` (vtbl+0x10, `0x80022788`) at `0x80021AE8`;
  detached-gravity falling branch `0x80021BD8..0x80021CD8`; `Teeter`
  (`0x80022B90`) at `0x80021D60` (common tail, gated on `0x74` bit 0x13 set /
  bit 1 clear); the `0xAC..0xB4` GetDeltaVelocity snapshot at `0x80021D68`;
  `Bob` (`0x80023190`) at `0x80021DA8`; `OnXorZRot` (`0x800222F4`) at
  `0x80021DD0`; `MovePassengers` (`0x8002337C`) at `0x80021E00`. The `0x94`/
  `0x98` counters gate *which* branch runs (wait vs. start-move vs. Move) with
  three decrement sites: `0x800219E8→0x80021A94`, `0x80021D08→0x80021D38`,
  `0x80021AA0→0x80021AB4`. Running `Think` every update (required so `Move`
  refreshes `0xA0..0xA8` every update for the collision gate) makes each of
  those tick k× too fast unless individually held — this is the part of the
  conversion that a register-equivalence test cannot prove correct, because a
  mis-held counter desyncs only a *pausing* platform in some later level that no
  headless route reaches.

- **The two reported cars are continuously-moving** (`0x78≠0`, `0x7c==0`,
  `0x98==0`), so they take the `Move` branch with **zero** counter involvement.
  The bug-fixing core (divide `Move` speed, divide `Teeter`, run `Think` every
  update) is therefore correct and testable for them independently of the
  counter-holding tier; the counter tier only protects pausing platforms
  elsewhere.

- **Live motion-trace settled the carry mechanism (2026-08-07).** A retail
  30 Hz `--motion-trace` of a player standing on the moving level-three car
  shows `pz` advancing ~181 per game update with `vx=vz=0` **and** `ex=ez=0`:
  the rider is carried purely by `MovePassengers`'s position add, with zero own
  and zero carried velocity, `py` constant. The 60 Hz trace (divided `Move`,
  no disembark gate) instead showed `ex/ez` non-zero on alternating updates
  (`SetCarried` still firing) and a net z-carry of ~123 per two updates vs
  retail's 181 — the backward lag — with the accumulating carried velocity
  eventually throwing the rider off (a −108 z lurch, then a fall). So dividing
  `Move` is necessary but **not sufficient**: the standing rider's ticket is
  still dropped every skipped update (per-update sink ≈ `9/k` < the 9-unit
  gate), and the ungated `SetCarried` at `0x8007C648` is the doubler/
  destabiliser. `retimedObstacleDisembark` (branch gate at `0x8007C624`) fixes
  it by deferring the whole disembark to the counted update, superseding
  `retimedLedgeTicketDrop`. Carried velocity then stays zero and the rider is
  carried by `MovePassengers` alone, as in retail.

- **The real moving-car carry defect is passenger-list membership, not the
  `Move` divide (2026-08-07, from Ghidra decompilation).** `MovePassengers`
  carries only the riders on `platform->0x40`, and a rider's membership *is* its
  ticket `humanoid->0xbc`. `HandleHumanoidObstacleCollision` rebuilds the list
  every update: `Disembark` (`0x8007C2C0`) clears the ticket at the top, then the
  obstacle's `HandleHumanoidCollision` re-issues it via `AddPassenger`
  (`0x80062400`, idempotent — only adds when `0xbc == 0`) **only when
  `CorrectThingPosition` reports a downward penetration and `vel.y <= 0`**
  (the `bVar3` gate → `vtable[0x38]`). At rate `k` a standing rider sinks only
  ~`gravity/2k` per guest update, so that penetration — and therefore the
  re-issue — fires intermittently; on the updates it misses, the rider is off
  `0x40` and `MovePassengers` skips it. That, not the horizontal `Move` divide,
  is the moving-car slide (retail carries the rider with vel and carried vel
  both zero — pure `MovePassengers` position add — so the only variable is list
  membership). `retimedPassengerHold` holds the top `Disembark` on skipped
  updates so the ticket persists and the rider is carried every update; the
  counted update still rebuilds, disembarking a rider that has genuinely left.
  `retimedObstacleDisembark` handles the symmetric end-of-pass drop. The
  `Move`-speed divide and `Think` reshape remain necessary for the swept gate to
  see matching per-update motion, but are not sufficient alone.

- **The `Move` speed divide is a single site.** `Platform::Move` reads `0xB8`
  into `$a1` at `0x800227D0` and passes it to the path advance
  (`jalr` at `0x800227DC`); dividing `$a1` there advances the path a k-th, so
  `newPos-oldPos ≈ 0xB8/k`, which is below the `±0xB8` clamp and never binds it.
  At k=2 a half-to-even divide (the `retimedPositionStep` body) is exact per
  authored frame; the six clamp reads can stay full-value. `retimedPlatformMotion`
  (the current hold of `Move` at `0x80022790`) is deleted by the conversion.

- **A held `Move` must preserve a bobbing Platform's Y pose (2026-08-09).**
  `Bob` is an authored-rate timeline and remains gated at `0x80021DA8`, but
  `Move` still runs each sub-step to advance the path. It snapshots the current
  (already bobbed) position at stack `+0x10`, then overwrites Platform position
  from Path position at `0x80022814..0x80022828`. On a held update that replaced
  the bobbed Y with the path-base Y; the next counted `Bob` restored it, making
  a standing rider in `vibrating.stsm` alternate between Y `-387` and `-412`.

  The semantic hook at `0x80022814` detects a live `Platform+0x130` BobType on
  held updates, keeps the old Y from stack `+0x14`, and replaces the saved Path
  Y at stack `+0x24` as well. The latter makes Move's following delta calculation
  publish zero vertical carry for that held sub-step. It still copies Path X/Z,
  so ordinary sub-stepped translation continues. Running `Bob` wholesale on
  every update was rejected: its mutable angle history and passenger rotation
  side effects replayed and ejected the rider. Refreshing standing collision on
  held updates was also rejected because it amplified the correction. The final
  probe stays aboard and follows the slow bob, with only the normal two-unit
  standing settle instead of the 25-unit pose alternation.

- **Running across a dynamic Platform needs continuous contact without
  accumulated grounded gravity (2026-08-09).** In `runleft.stsm`, keeping the
  whole obstacle pass gated made the player alternate `AS_Run` (`0x0a`) and
  `AS_Fall` (`0x0d`): the held update missed the moving surface, then the
  existing airborne exception landed it again. `AS_Run` now uses the same
  narrow held call to `Obstacle::HandleHumanoidObstacleCollision` as the other
  contact states, without sub-stepping the full humanoid list.

  That removed the state flip but exposed a smaller 5-6-unit correction:
  `DynamicThing::Move` immediately reapplied divided gravity after the contact
  path grounded the runner, leaving Y velocity to alternate between `-9` and
  `-18`. The reference implementation in
  `C:\dev\pub\ReChan\src\ai\platform.cpp` corroborates the intended split:
  `MovePassengers` calls `Land` for a non-upward rider, while platform carry is

### Obstacle ledge hangs drop at a high update rate — root cause

Symptom: at 60 Hz the player latches onto a pushable or a breaking platform and
is dropped immediately, re-latching in a loop. World-geometry ledges are fine.
`--ledge-trace` showed one `Obstacle::LedgeCheck` per drop, rejecting on
`FACING` with `BOX`, `HANDBAND`, and `CLEARANCE` all true and the contact Y
stable.

The chain, read out of the code rather than inferred:

1. `Obstacle::LedgeCheck` builds its facing vector by `memset`-ing twelve bytes
   at `sp+0x30` and writing only sin and cos, so **facing Y is always zero**.
   Its test is `dot(contact normal, facing) < 0`, and `FUN_800934E4` is a plain
   three-component dot, so the normal's Y contributes nothing. `FACING` false
   with the geometry conditions true therefore means the collision produced
   **no horizontal normal at all**.
2. `Obstacle::CorrectThingPosition` (`0x8007B398`) gates its whole axis
   selection on a swept-AABB overlap whose vertical half is
   `min(prevY, currY) + humanoid->0x11C <= box.maxY - K84C`. With no axis
   chosen it returns zero normals and a zero result.
3. `Humanoid::PrepareLedgeLatch` places the hanging humanoid's origin exactly
   at the box top, so that overlap only holds once gravity has pulled it far
   enough down. The hang is a one-frame race.
4. `Player::_LedgeLatch` (`0x8003352C`) zeroes velocity `0x64/0x68/0x6C` on
   every call. `Move__12DynamicThing` advances
   `position += velocity + acceleration/2` then `velocity += acceleration`.
   Sub-stepping that is exact only while velocity accumulates: the `k` terms
   telescope back to `v + a/2`. Reset velocity every update and each one
   contributes `a/(2k^2)`, so an authored frame drops `a/(2k)` — `k` times too
   little. **The hanging player sinks at half speed at 60 Hz**, never clears the
   overlap threshold, no obstacle re-issues the ledge ticket, and
   `Obstacle::HandleHumanoidObstacleCollision` calls `Humanoid::LetGoOfLedge`.
   Only obstacle hangs hold a ticket, which is why world ledges never showed it.

The decisive measurement is the threshold itself. `$gp` is 0x800DC94C, cross-
checked because `$gp+0x850` is the scratch `Pushable::HandleHumanoidCollision`
sets to the humanoid radius and `CorrectThingPosition` zeroes, and it reads
zero at rest. The constants are `$gp+0x844` = 4, `+0x848` = 0x40, **`+0x84C` =
9**, `+0x854` = 0x20. Nine is exactly retail's per-frame gravity step,
`gravity/2 = 18/2`, to the unit. The gate is literally "has one frame of
falling happened since the snap".

Also corrected here: the ledge branch of `Pushable::HandleHumanoidCollision` is
gated on `humanoid->0x18 == 0`, and that field is the player flag - the same one
that gates the rumble call in the hit branch. **For the player, `LedgeCheck`
returning zero is the correct path**, and a false `FACING` in the trace is
expected rather than the fault. Three rounds were spent chasing it, which is
the cost of reading a diagnostic before reading the branch that consumes it.

`--retime-clock` carries two patches. `retimedLedgeLatchVelocityReset` holds the
velocity reset on skipped updates, restoring the full 9 units of sink per
authored frame. `retimedLedgeTicketDrop` gates the `jal Humanoid::LetGoOfLedge`
at `0x8007C650` on the counted update - the end of an authored frame, the only
point at which a full frame of gravity has accumulated and a missing ticket is
therefore real. An unretimed divisor holds nothing and decides every update, as
retail does. An earlier revision gated on the *first* update of a frame, where
almost none of the sink has happened; it did not work.

Two hypotheses were tested and rejected along the way, both recorded because
they narrow the space rather than widen it: the humanoid turn rate (a real
unretimed per-frame quantity, fixed, but the trace was unchanged by it), and
the carried-velocity decay (also real, also fixed, also not this).

Process note worth keeping: two sampling trampolines built for this
investigation broke ledge attachment outright while every executable test
passed, because they used `$t2`/`$t3` as scratch. The MIPS ABI says a caller
must not rely on `$t0`-`$t9` across a call; retail does anyway — stock
`Obstacle::LedgeCheck` never writes `$t3` at all. A trampoline may only use
scratch its host function already destroys, plus `$at`. The equivalence test
now compares the whole register file, stock versus patched.

### Humanoid turning had no retiming at all — real, but not the ledge cause

`FaceAngleY__8Humanoid` (`0x80064EB0`) is the shared rate-limited yaw
integrator, the rotational counterpart of `Move__12DynamicThing`. It wraps the
difference to the requested heading into +-0x8000 and clamps the change to
field `0x156`, the maximum turn for one game frame, loaded once per signed
branch:

```text
80064F08  bgez $v1, 0x80064F38
80064F10  lh   $a2, 0x156($a0)   ; negative branch
80064F2C  subu $v0, $v0, $a2
80064F38  lh   $a2, 0x156($a0)   ; positive branch
80064F54  addu $v0, $v0, $a2
```

Applied once per guest update, that is `k` times retail's angular speed. The
caller's unlimited path (`$a2` zero on entry) snaps straight to the target and
must not be divided.

This was hypothesised as the cause of the obstacle ledge drop and **is not**.
`--ledge-trace` at 60 Hz shows one `Obstacle::LedgeCheck` per drop rejecting on
`FACING` — the sign of `dot(contact normal, humanoid facing)` — with `BOX`,
`HANDBAND`, and `CLEARANCE` all true and the contact Y stable at 2048. Because
`Humanoid::PrepareLedgeLatch` sets the yaw from that normal when the hang
begins, a doubled turn rate looked like it would cross the sign change in half
the authored time. Retiming the limit changed the trace not at all: same
condition, same values, same rate. The failed prediction is recorded here
because it rules the heading out and leaves the contact normal as the operand
to explain — hence `ledgeTraceFacingInputs`, which samples both operands and
the dot at `0x8007BF7C`, before `$s1` stops being the normal.

The turn-rate division stands on its own: the limit really is a per-frame
quantity and really did run at `k` times retail's angular speed.

`--retime-motion` divides the limit at both loads. A limit that divides to zero
is raised back to one, so a slow turn crawls rather than stalling; truncation
otherwise loses under one unit of a limit in the hundreds. The executable test
runs the whole retail function, so it covers the wrap, both signed branches,
the unlimited path, and a target closer than one step.

### Carried velocity decays per frame, not per authored step — verified

`Move__12DynamicThing` keeps two velocities. `0x64/0x68/0x6C` is the thing's
own, and `0x70/0x74/0x78` is momentum carried from something it rides, hangs
from, or is pushed by. The carried triple is lifted out of the own velocity at
the top of the function, folded into the position step, added back at the
bottom, and its X and Z components are decayed there by one shared 16.16
factor:

```text
800622C0  lw    $a1, 0x6d0(gp)    ; the decay factor
800622D8  mult  $a1, $a0          ; carried.x
80062318  mult  $a1, $v1          ; carried.z
```

The step is already divided by `retimedPositionStep`, so the distance the
carried velocity contributes is right. The decay is not: it is a per-frame
quantity, so at `k` guest updates an object sheds borrowed momentum `k` times
as fast in wall-clock terms. Y is deliberately never decayed, in retail and
here.

`0x800622C0` is the position site's own delay slot, so the factor is already in
`$a1` when the trampoline body runs and both multiplies read it afterwards.
Substituting `0x10000` on a held update makes both decays the identity and
spends retail's decay exactly once per authored step, with no second site and
no branch around the stores.

Predicted consequences, awaiting live confirmation: a humanoid hanging from a
moving obstacle loses its tracking of that obstacle in half the authored time
at 60 Hz, which drops the obstacle ticket and reaches
`Humanoid::LetGoOfLedge` through `Obstacle::HandleHumanoidObstacleCollision`,
and a jump from a moving platform keeps less of the platform's momentum.

Also read out of the same function while tracing this: gravity is reloaded to
`0x12` at the end of every `Move__12DynamicThing`, so the player's gravity is
18. That is even, which is why `retimedGravity`'s half-to-even division is
exact at a divisor of two. It is not exact at three or four — 18 divided by
four rounds to four each update, or 16 per authored step — so the boot
executable's per-frame acceleration is understated above 60 Hz. Retail
integrates as `position += velocity + acceleration / 2` and then
`velocity += acceleration`, so the error shows up as jump height. A divisor-
independent fix is to replace the per-update rounding with a telescoping
partition, `floor(g*p/k) - floor(g*(p-1)/k)` over the update's phase `p` in
`1..k`, which sums to `g` exactly for any `k` and any sign.

### The loader assumes the game loop runs at half the VBlank rate — verified

Retail services two independent task lists on two different clocks:

| Driver | List | Clock |
| --- | --- | --- |
| `MyVBL__Fe`, at `0x800261C8` | `0x800DE0A0` | VBlank, a fixed 60 per second |
| the main game loop, at `0x80026460` | `0x800DDF78` | one per game frame |

At the retail 30 Hz update rate the game loop runs at half the VBlank rate, so
anything on the VBlank list gets two slices per game-loop slice. Unlocking the
30 Hz swap gate makes the game loop run every VBlank and collapses that ratio
to one to one.

The level loader is a streaming producer/consumer pipeline split across those
two clocks. Compressed data is read from CD to about `0x801E5BD0`, expanded by
`SquExpandData__FPUcT0` (`0x80093DB4`) into a staging buffer at about
`0x801FD600`, and uploaded to VRAM in 256-byte tiles by the `LoadImage` helper
at `0x800281B0`, which sends a few words by CPU store and the bulk by a DMA2
block transfer. Watching writes to the staging buffer shows the two sides
strictly alternating: expand a chunk, upload a batch, repeat.

Losing the 2:1 budget lets the consumer outrun the producer, so tiles are
uploaded before they have been expanded. The result is byte-level, not a
rendering artifact: the same texture tile at the same VRAM address in the same
level decodes to a clean floor with 57 distinct halfwords at 30 Hz and to
static with 199 at 60 Hz. Because the decoder mirrors the hardware, real
hardware fed those bytes would show the same static.

This is a retail design invariant rather than a host defect. Running the game
loop at 60 Hz through a load would require rebalancing retail's streaming
pipeline, so the host must retain retail cadence for the load states.

GPU upload activity proved to be the wrong way to identify those states. The
prepared gameplay save continuously calls `PaletteData::TransferVram` for a
visible `WEffect`, uploading a 256x1 CLUT row at VRAM `(768,196)` every authored
frame with no CD reads. Walking away makes the effect leave view and stops the
uploads, which explains why the old 90-publication quiet heuristic appeared to
switch retime back on. Pause UI and RAM texture animation provide other valid
gameplay uploads, so no quiet threshold can avoid both false positives and a
visible re-enable delay.

The current selector instead reads `theGameMgr` at `0x800DD668` and its
`Game::pStateHandler` field at `+0x1c`. Retail publishes the next handler before
the current `Step` returns. Known steady handlers, including `gsPlayState`
(`0x80029C6C`) and `gsMenuState` (`0x80029EF8`), engage high frequency on that
publication; load/transition handlers and unknown values fail closed to the
retail schedule. A cold scripted route observed title loop -> queue level ->
play with two unlocks and one relock. The prepared palette-upload save stayed
unlocked, and opening pause changed to `gsMenuState` without relocking. This
keeps the loader's 2:1 invariant while removing the old quiet-window delay.

A controlled 16x probe established that the high-frequency request was not
itself accelerating pre-switch audio: stock 30 Hz and requested 60 Hz WAV
captures were byte-identical through VBlank 650, and their first PCM difference
was in VBlank 651, after the swap gate had engaged. The 16x bulk-read setting is
intentional for short loads. In requested-60 mode, accelerated completion now
falls back to console 2x after 30 upload-quiet publications during a load and
returns to the requested rate when a steady handler is published or uploads
resume. Upload traffic controls only this CD settling tail, not guest cadence.

Confidence: the two clocks, the pipeline, its alternation, and the byte-level
difference are all verified. Which specific task sits on which list is inferred
from that structure and has not been read out of the task lists directly; doing
so is the remaining confirmation.

### Level geometry is culled against a hardcoded 4:3 screen — verified

At a window wider than 4:3, PsyCross widens its 2D ortho by the window aspect,
adding view at the sides rather than stretching, so anything retail submits
outside its 512-wide screen lands in the margins. Retail culls most of it.

The dominant cull for level geometry is `RP_ZCullGClip__FP9tGeometry`
(`0x800A0E14`), reached from `Draw__5BlockRC10tagLVector`. It carries its own
Cohen-Sutherland outcode with the screen bounds baked into immediates rather
than read from the clip box:

```text
800A0E48  lui  $t8, 0x100       ; t8 = 0x01000200, y limit 256, x limit 512
800A0E54  ori  $t8, $t8, 0x200
800A0E68  lui  $t5, 0x4000      ; t5 = 0x40004000, bit 14 means coord < 0
...
800A0FD4  subu $a1, $t8, $v1    ; limit - coord
800A0FD8  and  $a1, $a1, $t7    ; sign bit: coord > limit
800A0FDC  and  $v1, $v1, $t5    ; bit 14:   coord < 0
800A0FE0  or   $v1, $v1, $a1
800A0FE4  and  $v0, $v1, $v0    ; AND across vertices: cull if all outside
```

Because the bounds are immediates, widening `_5tPort.CB` has no effect here.
Raising the right limit and clearing the low half of the `< 0` mask makes the
edges fill in, live-validated at 1280x720.

Props and characters are culled by a second, independent path:
`P3DClipCode__FUlUl` (`0x8009E218`), reached through
`P3DClipCodeSphere__FP7tSphere` from `Show__6GModel`, `Show__6SModel`,
`Show__6EModel`, `Display__6tETree`, and `PointInView__9ComEffect`. Unlike the
block cull it does read the clip box:

```text
8009E248  and  $v0, $a0, $a2    ; sign bits: x < 0, y < 0
8009E260  lh   $v1, 0x60($v1)   ; maxX from the clip box
8009E270  and  $a0, $a0, $a2    ; sign bits: x > maxX, y > maxY
```

`P3DClipCodeSphere` keeps a *second* copy of maxX at `0x8009E2D8` for a
radius-aware path it takes only when that quick point test rejects:

```text
8009E2D8  lhu  $s6, 0x60($v0)   ; maxX, loaded again
8009E3AC  subu $v0, $v1, $a0    ; centre x - projected radius
8009E3B0  andi $v1, $s6, 0xFFFF
8009E3B8  beq  $v0, $zero, cull
```

Both bounds must widen. Widening only the point test produces a distinctive
asymmetry that named the missing site: objects entering from the left appear on
time while objects entering from the right stay late. Left-side objects pass the
quick test outright once its lower bound is gone and never reach the second
check; right-side objects fail the quick test, fall into the radius path, and
meet the original 512.

Both culls are widened by `--widescreen-cull`, live-validated at 1280x720:
level geometry fills the edges and props enter on time from both sides.

The setting is now reversible at a guest-worker safe point (`F8`, or the
experimental Display menu); both paths also select the paired render target.
`setWidescreenCull` recognizes the untouched retail
sites or one complete patched set with any prior immediate limit, restores all
recognized retail words and trampoline sites, then applies the current
seventeen lower-bound patches. This is also run against a decoded quick-save
candidate before the candidate may replace the live machine. Widescreen flags and render dimensions
therefore no longer reject a save made under the other presentation choice; an
old exact-edge patch (for example the 16:9 limit 597) is normalized to the
current setting transactionally with the rest of candidate validation.

#### The left bound is the near-plane cull — verified

Dropping the lower X bound rather than widening it was wrong, and the symptom
was the in-game HUD being covered by level geometry: intermittently before the
widescreen work and constantly after it.

`RP_ZCullGClip` has **no Z test at all**. Its only rejections are `NCLIP`
backface removal and the screen-space outcode, so the outcode is also what
removes geometry behind the camera. A vertex behind the eye divides by a
clamped `SZ3` of zero, leaves the GTE with its screen X saturated to `-0x400`
or `0x3FF`, and reaches the ordering table at `minZ >> shift` — index zero, the
nearest slot, drawn last. Retail catches those polygons because every vertex
lands outside the same screen edge. With the left edge removed from the test
they survive, and each one is a screen-spanning quad drawn after the HUD.
`P3DClipCode` lost both its X and its Y lower bound the same way, which let
whole objects behind the camera through at the object level.

Neither bound can be moved by changing an immediate. Both express "coord < 0"
as a single bit test — bit 14 of the packed pair in `RP_ZCullGClip`, the sign
bit in `P3DClipCode` — and screen X is an 11-bit saturated GTE result, so
within its range no other bit position, mask, or limit means anything else.
The right bound is a real comparison (`limit - coord`, tested for sign), which
is why only that side could be widened in place.

The fix biases the coordinate by `x_limit - 512` before the existing bit test,
which moves the threshold to the widescreen left edge while the right bound
keeps reading the unbiased value. That needs a second instruction, so it is a
trampoline per site: fourteen byte-identical outcode blocks in
`RP_ZCullGClip` (four per quad loop, three per triangle loop, each beginning
`subu $a1, $t8, $v1`), plus `P3DClipCode`'s point test and the radius-aware
left test in `P3DClipCodeSphere`. The bias is added to the packed pair, so it
has to be masked back out of the Y half: a vertex with X in `[-bias, -1]`
carries into Y and would otherwise clear the Y sign bit of the vertex above it.

Biasing in the `nop` after each `mfc2` would have made this fourteen one-word
patches instead of fourteen trampolines. It is wrong: that `nop` is the
coprocessor load delay, and `R3000Runtime` models it, so the biased instruction
would read the previous vertex.

Experimental NCLIP margin guards used the transformed-vertex pointers already
live in each polygon loop, but positive depth was not enough to distinguish a
wide visible polygon from the back-facing wall strips in `pokey-wall.stsm`.
Current mode leaves NCLIP and the final outcode untouched; their old sites are
retained only so quick-save normalization can remove the experimental jumps.

#### PsyCross must apply the GPU's oversized-polygon rejection — verified

The blocked-grid quick save reproduces the defect at retail 30 Hz, 800x600,
without `--widescreen-cull` or any retiming. Packet-bisecting its retained GP0

This is a hardware-compatibility gap in the PsyCross presentation path, not a
guest cull change. The PS1 GPU rejects polygons spanning more than 1023 pixels

### Retail runs its game step on the hardware scratchpad — verified

`0x80057D18` is a stack-switching trampoline: it saves `$ra` and `$sp` below
the supplied stack top, switches `$sp` to it, calls the supplied function, then
restores both. Retail calls it with `$a1 = 0x1F8003F8` from at least
`0x8002B33C`, `0x80054160`, `0x80055EA8`, and `0x8007EC8C` — the top of the
1 KB hardware scratchpad at `0x1F800000`.

This was found through a live fault. Injecting a host VBlank callback onto the
interrupted stack left the deeper 60 Hz `VSCallback__Fe` path without room, and
the guest died at `0x80028DA8` with `$sp = 0x1F7FFFD8`, exactly `0x28` below
the scratchpad base. Real hardware never had this problem: the BIOS exception
handler switches stacks before dispatching callbacks. The host now does the
same through `R3000Runtime::beginInterruptCall`.

### Native GPU boundary — verified

The guest submits GPU work through direct GP0/GP1 writes, DMA2 linked lists,
and DMA2 block transfers. The stateful decoder separates GP0 packets from
CPU-to-VRAM payloads and maintains 1024x512 16-bit VRAM. Packet data, VRAM,
display origin, and display mode are snapshotted together at GP1 display-start
flips; replaying an older frame therefore cannot sample textures overwritten
by later guest activity. Persistent GP0 E1-E5 state is seeded into each new
interval.

At 150 million instructions with a connected neutral pad, the selected frame
contains 996 primitives and renders the retail Jackie Chan title presentation
through PsyCross/OpenGL. Two adapter details were required:

- publish copied VRAM before PsyCross draw splits snapshot its double-buffered
  texture handle;
- decode GP0 XY fields and E5 offsets as signed 11-bit values, apply the draw
  offset and target origin, then convert to PsyCross's x64 PGXP half-float
  primitive representation before calling `DrawPrim`.

High-rate host interpolation has an additional coverage invariant. Packet
matching is deliberately conservative, so one polygon can match the previous
frame while its neighbour does not (a changed texture word is sufficient).
Interpolating only the matched polygon moves one copy of their shared edge
while the unmatched copy stays at the current position. The resulting gap is
transient and most visible during camera motion, where the clear or background
layer leaks through as a diagonal crack.

The interpolation map now indexes trustworthy previous positions by complete
normalized draw state plus current vertex position, and propagates that
position to every polygon occurrence of the shared vertex. Unmatched interior
vertices remain on the exact current frame. Conflicting previous positions at
one coincident vertex fail closed to current on all occurrences. A deterministic
test covers a matched world triangle beside an unmatched textured triangle and
requires both copies of the shared edge to receive the same previous position.

That only fixes interpolation disagreement. The captured first-level GP0
stream also contains 333 pairs of long adjacent polygon edges whose independently
projected endpoints disagree by one or two native PS1 pixels in the *same*
frame. The native rasterizer mostly hides these quantization seams; PGXP scales
the submitted coordinates before rasterization, turning them into visible
background wedges. Expanding polygon vertices is not a valid repair: live
testing showed it distorts independently projected faces and opens many larger
cracks. A future fix must change raster coverage without changing geometry.

DuckStation reproduces these seams when geometry upscaling is enabled, which
confirms that they are same-frame PS1 projection quantization rather than a
frame-interpolation defect. The distracting color differed because this
presenter composited the selected display page underneath a full 3D pass;
bright stale DMA/framebuffer contents showed through every crack. Display-page
composition is now retained for low-polygon DMA-built screens and suppressed
for a substantial world pass, leaving black behind the seams. Full PGXP
geometry correction is a larger follow-up: an emulator can retain precise
pre-rounding GTE/CPU values, while the current packet replay sees only the
already-rounded GP0 screen coordinates.

The identical retained title frame is still visible at 350 million
instructions, where execution stops at `0x8009FE2C` after 124 GPU callbacks
and 492 VSync callbacks.

Publishing at display flips removed post-Start checkerboard texture corruption;
signed-11-bit/E5 translation removed the oversized foreground geometry. The
live presenter clears both host backbuffers at startup and across the
title-to-world transition, removing title-buffer colors from uncovered
gameplay pixels, then preserves normal gameplay color history for one-shot
retail overlays such as the pause menu. Static replay and screenshot paths
remain independently cleared. `--window-size` exposes both 4:3 and
expanded-widescreen PGXP presentation. The
PsyCross screenshot helper writes OpenGL rows without flipping them, so
`SCREENSHOT.BMP` is vertically inverted; the native window does not share that
file-format artifact.

Gameplay also proved that one final VRAM image cannot texture every deferred
primitive. Retail reuses texture regions between submitted batches, so the
host retains an upload-backed VRAM snapshot only when a new revision is first
used by a primitive. PsyCross publishes and flushes those segments in order.
This removed broad world corruption.

A GP0 VRAM copy is applied only when its source region is entirely
upload-backed. The decoder tracks uploads but does not rasterize world
primitives, so a framebuffer-sourced `MoveImage` would copy bytes it never
saw written: one such copy overwrote the `facade` tile at VRAM `(192,160)`,
used by textured polygons with tpage `0x00C2` and CLUT `0x24F0`, visibly
corrupting the level-one torii. Upload coverage is the exact test for that
case, and it refuses this one. A copy whose source every pixel of which arrived
by CPU transfer moves bytes of known provenance, and retail needs it — see the
loading screen below. The destination becomes covered in turn, so a chain of
such copies stays sound.

### The loading screen is written, not drawn — verified

The level-load screen was appearing as its tutorial text on a black field, with
no background, and the same transition's fade was missing. Retail does not draw
that screen. Captured from a real transition, one interval contains:

```text
A0 upload (512,256) 512x240      ; the whole background, straight into a page
80 copy   (512,256)->(0,256)     ; MoveImage, so both buffers carry it
```

and every following interval draws only the text — 34 textured quads, one per
glyph — over a framebuffer it expects to still hold the image. Decoding that
page out of a retained VRAM snapshot shows the artwork intact, "Loading" logo
and progress bar included, so the host had the pixels all along and simply
never composited them: it clears the backbuffer each interval and rebuilds the
frame from primitives alone.

The host therefore applies the copy, which puts the background into the second
page so the alternating pages do not flicker between image and black, and draws
the selected page back as the frame's base layer before replaying packets, as
two textured rectangles — a 15-bit texture page window addresses 256x256 texels
from `(X*64, Y*256)`, so a 512-wide page is two of them.

Getting there took two renderer bugs, both found by bisecting the pass against
`--replay-capture` rather than by reasoning:

**PsyCross skipped per-program sampler uniforms.** `GR_SetTexture` selects a
shader for the colour depth and then early-outs when the bound texture is
unchanged — but sampler uniforms are per-program state in GL, and every format
here uses the same `g_vramTexture`. A program entered that way has `s_texture`
and `s_lut` both defaulted to unit 0, so a 4- or 8-bit shader samples its
palette out of the VRAM texture. Everything drawn after a format switch
collapsed to about 1% brightness. The bisect is unambiguous: with the
background rectangle declared 4-bit the following text renders at full
brightness, and at 8- or 15-bit it drops to a maximum channel value of 3.

This was never specific to the composite. It is why the reference title capture
had always been dark, red and heavily dithered: the title switches format
mid-frame, and everything after the first switch was sampling its palette from
the wrong texture unit. With the early-out also requiring an unchanged program,
the title renders in its proper colours.

**A rectangle's size is half-float in a PGXP build.** `SPRT` declares
`VERTTYPE w, h`, not `short w, h`. Left as plain integers, 256 and 240 read
back as subnormals, all six vertices collapse onto one point, and the rectangle
rasterizes to nothing — which is exactly what the vertex trace showed, every
corner at `(-0.5, -0.5)`.

Two more facts worth keeping. **PsyCross textures a rectangle from
`activeDrawEnv.tpage`, not from the packet**, while textured polygons carry
their own `tpage` and assign it to that state as a side effect; `DR_TPAGE`
masks with `0x1FF`, so the page base and colour depth survive while dither and
draw-to-display are read separately. And the base layer is safe to leave on:
replaying captured gameplay frames with and without it is pixel-identical,
because the authored 4:3 area is 0.0% uncovered by world geometry.

### PAD boundary — verified

`ReadSonyPads__Fv` treats byte zero of `padZero`/`padOne` as connection status,
then inverts bytes two and three into the game's active-high button word.
`PadInitDirect` initializes the two caller-provided buffers to no-device state.
The live host refreshes port one at each VBlank as a connected digital pad and
leaves port two disconnected. PsyCross/SDL supplies an active-low button word
from remappable keyboard and gamepad bindings. Early keyboard input at the
title reaches the player-selected gameplay route. The earlier apparent
Return/Start and `S`/D-pad Down observations predated the fixed host byte
order: they prove that a non-neutral word reached retail code, but cannot be
used as evidence for those individual button identities.

Circle/Right tracing exposed two compensating byte-order errors. PsyCross
clears logical active-low bit `0x2000` for Circle and stores its host-side
`PADRAW::buttons` through a native-endian `u_short`. The original presenter
swapped those bytes while polling, but RetailHle also wrote its supplied word
high-byte first. Together they happened to produce the correct direct-pad wire
bytes while making the host trace label Circle as Right.

The corrected boundary keeps one normalized logical word in the host:
Circle `0xDFFF`, D-pad Right `0xFFDF`, and Start `0xFFF7`. RetailHle serializes
the low byte followed by the high byte, so Circle writes `FF DF` to
`padZero+2`. `ReadSonyPads__Fv` at `0x8002D830` deliberately combines the two
wire bytes high-first and inverts them, producing retail/Psy-Q active-high
Circle `0x0020`, D-pad Right `0x2000`, and Start `0x0800`.
`ServiceInput__12InputManagerUlUs` at `0x8002E0D4` then passes that convention
into the retail `Control` objects. Tests lock all three conversions. Retail
Circle is contextual grab/interact, which explains no animation when nothing
grabbable is in range. The host's `--input-trace` observes the normalized host
word without injecting input.

### Semantic mouse input and player-facing seam — verified

The eight bytes at `*(0x800DD69C)+0x2E0` are the current port-zero
physical-to-logical `Control` map. The exact three retail layouts at
`0x800D64A4` are permutations of logical Status, Strafe, Counter, Dive Roll,
Kick, Grab, Jump, and Punch. Translating a mouse semantic through the inverse
of this live map, then applying host PAD bit `physical ^ 8`, lets
`ReadSonyPads`, `Control`, `FindButtonMapping` (`0x8002E754`), and the 20-entry
command table keep deriving all chords, directions, and holds normally.

Mouse input is gated on `gsPlayState` (`0x80029C6C`), a valid `thePlayer`
(`0x800DD6B4`), and Behaviour handler `PlayerUserControl` (`0x80074F5C`). It is
therefore absent from pause (`gsMenuState`, `0x80029EF8`), the front end,
movies, loads, NIS control, invalid object transitions, and photo mode.

Retail's own stick mapping computes
`cameraYaw - rmATan216(x, -y) + 0x4000`, equivalently
`cameraYaw + atan2(x, -y)`. Gameplay mouse orientation uses that same two-axis
screen convention; integrating horizontal deltas as yaw was rejected because
a closed circular gesture cancels instead of describing a turn. Retail's
digital pad reader ignores `padZero+4`; the host publishes the resulting yaw
there and a mode byte at `padZero+8`. A reversible trampoline displaces the
final `jal RequestAction` at `0x80075398`, after retail has already computed
its camera-relative `faceAngle`. Camera-relative mode stores mouse yaw in
`Player+0x2c`, preserves that travel angle, and maps ordinary Run action 2 to
authored Strafe action 6 only while `Player+0x164` is Stand (1), Run (10), or
Strafe (11). Contextual states retain action 2: notably, launcher-driven
`Player::_Flip` checks command bit 2 before applying directional force, so an
unconditional replacement makes bouncy surfaces immobile. Falls, pushing,
ladders, and other special handlers also consume that bit directly.
Character-relative mode instead rotates the travel
angle by `mouseYaw - cameraYaw` and retains Run. Non-movement and stationary
requests set both orientation and face angle to mouse yaw.

`Player::_Straif` normally acquires a foe at `0x80034010`. A second trampoline
keeps the stock branch in mode zero, while either mouse-facing mode skips
acquisition and calls retail `ReleaseTarget` (`0x80065200`) for an existing
target. Its animation table at `0x800D91E0` remains untouched.

Both sites verify their complete neighboring instruction windows before either
is changed, install transactionally at patch-arena offsets `+0x000` and
`+0x200`, and restore the exact displaced words. Emulator tests execute the
camera-relative, character-relative, target-release, no-target, and stock
branches with architectural R3000A load delays; this caught and corrected an
initial unscheduled-load draft before live use.

Live validation rejected both movement policies as final designs: universal
Strafe changes locomotion and interaction semantics, while character-relative
Run causes severe motion discomfort. The exhaustive consumer and ownership
inventory is recorded in [MOUSE_HEADING_AUDIT.md](MOUSE_HEADING_AUDIT.md).
The proven replacement architecture is in
[MOUSE_DUAL_HEADING_DESIGN.md](MOUSE_DUAL_HEADING_DESIGN.md). It keeps
camera-relative Run and Move, gives free locomotion, ambient Player idle, and
ordinary airborne states a scoped mouse-facing lease, normalizes context ownership at Player
action transitions, and reuses directional Strafe animations without entering
Strafe state. The two-hook
implementation described above remains useful prototype evidence, not the
shipping movement architecture.

### Dual-heading mouse locomotion — implemented and emulator-tested

The final implementation replaces the prototype with thirteen transactional,
fingerprinted resident seams: action ownership at `0x800303D8`, Stand movement
at `0x80031534`, Stand final facing at `0x800319A8`, Run stop animation at

### Vibration boundary — verified

The game links its own Sony libpad copy (boot `0x8005A674`..`0x8005C1A8`),
whose pad-detection state machine runs in the SIO interrupt handler
(`_padIntPad`, `0x8005AD24`). This host emulates neither the SIO port nor its
interrupts, so the machine never runs and the driver's per-port state byte
stays at its BSS zero — which is why the game saw no vibration support.

- The per-port structs are 0xF0 bytes at `0x800E28FC` (port 0) and
  `0x800E29EC` (port 1), reached through the pointer at `0x800D89F0` set by
  `_padInit` (`0x800AD78C`, called from `PadInitDirect`).
- `PadGetState` (`0x8005A824`) returns the raw state byte (+0x49) whenever
  the struct is in the clean condition — b37/b38/b39 zero, `next == self`
  (set by `PadInitDirect`), direct-buffer byte zero — which the host
  maintains; the value mapping at `0x8005A898` (`{2,3} -> 1`, `6 -> 4`)
  applies only to transient/error conditions with commands pending.
- The state byte reaches 6 only through the SIO act-info load (`0x8005C0A8`,
  with mode byte +0x46 set to 0xFE; the load starts at state 4, `0x8005BBC8`).
  The game gates vibration on `PadGetState(0) == 6`: the Options vibration
  toggle (`0x8002E620`), the shake function (`0x8002D6C0`), and the shake
  countdown pump (`0x8002D5A4`).
- The host publishes the DualShock fields on every VBlank in
  `RetailHle::onVBlank`, self-healing against the driver's struct reset
  (`0x800AD87C`): state 6 (+0x49), mode 0xFE (+0x46), actuator count 2
  (+0xE4, `PadInfoMode` info 3), comb count 1 (+0xE3), mode-switch mask 0x73
  (+0xE6, info 1), current mode 0x41 (+0xE8), layout 1/2 (+0xE9/+0xEA).
- Motor values: `SetVibration` (`0x8002D540`) writes motor A to `0x800DD6AC`
  and motor B to `0x800DD6AD` (the `PadSetAct` table at gp+0xd60; Sony
  order, big then small) plus the shake countdown at `0x800DC9D8` (gp+0x8c);
  the pump clears the table when the countdown expires (`0x8002D52C`). The
  guest worker reads those three words and the main thread applies
  `SDL_GameControllerRumble` (big -> low frequency, small -> high), which
  needs no SDL haptics subsystem.
- The rebuilt Driver 2 `pad.c` in the REDRIVER2 checkout confirms the same
  SDK generation's convention independently: per-frame
  `PadSetAct(port, motors[2], 2)` with motors[0] = big/alarm and
  motors[1] = small/speed, gated on `PadGetState == PadStateStable` (6).

### The render queue completes layers by polling, not by callback — verified

`VSCallback__Fe` completes a queued swap at `0x800A0188`: it calls the display
and draw environment setters with the *same* index out of `RenderQueue+0x20` and
toggles that index afterwards. Retail's two environments are complementary, so
one index selects a display page and the opposite draw page.

`QueueLayer__11RenderQueueUl` installs the DrawSync callback at `0x8009FF48`,
and only `DSCallback__Fe` removes it, when the queue drains. The callback is
therefore persistent, not one-shot.

Retail does not depend on it here. The host's `DrawSync` boundary reports the
GPU idle immediately, so `WaitForLayer__11RenderQueueUl` frees its layer by
polling and the callback is redundant. Injecting it anyway dequeued layers
retail had already retired, advancing the queue a second time and toggling the
buffer index twice per frame — which pinned the draw environment to one VRAM
page while the display kept alternating. Measured before the fix: 72 queued
layers against 36 delivered completions, `WaitForLayer` entered 1.75 million
times, and page `(512,256)` never receiving a single primitive across a whole
probe.

### Retail's CD loader polls for a remaining sector count — verified

`0x8007EF20` is the only caller of both `CdRead` (`0x8007EF5C`) and
`CdReadSync` (`0x8007F020`). It polls in mode 1 and branches on the remainder:

```text
8007F01C: addiu $a0, $zero, 1    ; mode 1 = poll
8007F020: jal   0x800b88c0       ; CdReadSync(1, 0)
8007F028: blez  $v0, 0x8007f038  ; at or below zero -> finished
8007F034: addiu $v0, $zero, 5    ; above zero -> state 5, come back later
```

So a positive remainder is what the loader is built to handle, and reporting one
is how a screen shown during a load gets its duration. Two rules follow, the
second of which cost a runaway to 847,327 reads: report the remainder only in
polling mode, because mode 0 blocks on hardware and can only ever report
completion; and a fresh `CdRead` supersedes the outstanding one rather than
adding to it, because the loader re-enters while a read is in progress and
issues the next chunk.

The splash screen is 315 sectors long — 2.1 seconds on a double-speed drive, and
one VBlank with instant reads, which is why it was invisible.

### Retail drives the SPU through hardware registers — verified

Retail links its own copy of Sony's `libspu`, so it never calls PsyCross's
reimplementation of that library. It writes the hardware register file at
`0x1F801C00` directly. Measured over a scripted run into gameplay: 1,096
register writes, 32 key-ons, 56 key-offs, and 1,119,440 bytes of samples
uploaded into sound RAM through DMA4, with `SPUCNT` at `0xC0E1` — enabled,
unmuted, reverb master on, IRQ9 enabled.

### Music streams through a voice pair refilled by the SPU interrupt — verified

Voices 9 and 10 are the stereo stream: voice 9 at `0x2DC70` repeating to
`0x3DC70`, voice 10 the right channel at `0x35C70` repeating to `0x45C70`, both
at pitch `0x800`. The IRQ address sits just past voice 9's repeat point.

`SpuSetIRQCallback` is `0x800C79EC` and stores its argument at `0x800DBF1C`,
next to the transfer callback at `0x800DBF18`. Retail registers
`SPUAddrCallback__9rsdStream` (`0x800B99B4`) there and refills the half of the
buffer it is not playing when the interrupt fires.

Two host-side rules make that work. The repeat-address register moves the loop
point immediately and overrides whatever a block's loop-start flag set, because
retail points a *playing* voice at the half it has just refilled. And key edges
take effect when the register is written, not at the next mix — deferring them
resets the voice after the guest has already written the repeat address, which
discards the one write that matters. With both, the interrupt fires and retail
streams 262 KB more audio than without.

### Retail leaves the hardware ADSR at zero — verified

Every voice has `adsr_lo` and `adsr_hi` at zero, and the current-volume register
at `voice+0xC` is never written. Retail takes the hardware default: all-zero
rates snap the envelope to maximum and hold it there, with a fast release on
key-off.

Implementing ADSR therefore changes the mix not at all — a capture is
byte-identical before and after, peak 31337 against 31338. Levels come entirely
from the per-voice volume registers, which are plain levels rather than sweeps:
every one observed is below `0x8000`, and the main volume is `0x3FFF`. Per-voice
values of 16383, 13107 and 12123 are 0.99, 0.80 and 0.74 of full scale under the
register format's doubling.

### Retail reverberates SFX, not music — verified

At the end of the same scripted gameplay probe, `SPU_REVERB_ON` is `0xFFF9FF`.
That is every voice except 9 and 10, the stereo streaming pair established
above. Reverb is therefore an effects send for the sound effects; music remains
dry. `vLOUT` and `vROUT` are both `0x0BB8`, only about 9.2% of full scale, so the
intended return is subtle rather than a second full-volume copy.

`mBASE` is `0xF6F8`, byte address `0x7B7C0`, which reserves the final 18,496
bytes of sound RAM. The 32 effect registers retail leaves behind are:

```text
00B1 007F 70F0 4FA8 BCE0 4510 BEF0 B4C0
5280 4EC0 0904 076B 0824 065F 07A2 0616
076C 05ED 05EC 042E 050F 0305 0462 02B7
042F 0265 0264 01B2 0100 0080 8000 8000
```

The host now consumes those registers as hardware does: voice routing is an
additive send, processing runs at 22.05 kHz through the circular sound-RAM work
area, and a fixed FIR pair converts to and from the 44.1 kHz output clock. In a
matched 520,380-frame capture the effect changes 201,441 samples, never clips,
keeps the same peak of 25,185, and raises overall RMS only from 2,404.6 to
2,408.3. Those measurements fit the programmed 9.2% return and close reverb as
the cause of a gross level imbalance.
